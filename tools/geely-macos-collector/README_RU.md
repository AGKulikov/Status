# Досбор недостающих файлов KX11 с Mac

Этот комплект собирает конкретные пробелы, установленные после повторного разбора переданных дампов. Запустите `Collect-KX11.command` и пришлите созданный архив `KX11-Missing-Evidence-….tar.gz`, даже если результат обозначен `PARTIAL`.

## Запуск

1. Распакуйте **KX11-Missing-Files-macOS-v1.0.0.zip** целиком. Оставьте `Collect-KX11.command`, `collect_missing.py`, `collection_plan.json`, `known_files.json.gz` и папку `lib` рядом.
2. Подключите Mac к включённой ГУ тем же способом, которым раньше работал ADB. Автомобиль должен стоять. На Mac нужны существующий `adb` и Python 3.8 или новее; сторонние Python-пакеты не нужны.
3. Откройте `Collect-KX11.command`. В конце он покажет путь к архиву на Рабочем столе. Пришлите сюда этот `.tar.gz` и соседний `.sha256`.

Если macOS не открывает `.command`, откройте Terminal, введите `bash `, перетащите туда `Collect-KX11.command` и нажмите Enter. Второй вариант из папки комплекта:

```bash
python3 collect_missing.py
```

Если Python или ADB отсутствует: [установщик Python для macOS](https://www.python.org/downloads/macos/) и [официальные Android SDK Platform-Tools](https://developer.android.com/tools/releases/platform-tools). Распакованную папку `platform-tools` можно положить рядом с `collect_missing.py`. Скрипт также ищет ADB в PATH, `/opt/homebrew/bin`, `/usr/local/bin` и `~/Library/Android/sdk/platform-tools`. Установку инструментов он сам не запускает.

При нескольких подключённых ADB-устройствах сбор не выбирает автомобиль наугад:

```bash
adb devices
python3 collect_missing.py --serial "СЕРИЙНЫЙ_НОМЕР_ГУ"
```

Путь к уже установленному ADB и другую папку результата можно указать явно:

```bash
python3 collect_missing.py --adb "/путь с пробелами/platform-tools/adb" --output "$HOME/Desktop"
```

`unauthorized` означает, что требуется штатное подтверждение подключения на ГУ; `no_device` — что текущий ADB ещё не видит её. Скрипт использует существующие права ADB, включая уже работающий root-adbd, но не выполняет `adb root`, `su`, перезапуск служб или поиск сетевых устройств. Отказ чтения попадёт в отчёт.

## Что именно будет получено

Полный ограниченный перечень, причины и исходные доказательства находятся в [collection_plan.json](collection_plan.json). Для просмотра без подключения:

```bash
python3 collect_missing.py --plan
```

| Группа | Зачем нужна |
|---|---|
| `XCHvac.apk`, пакет `ecarx.hvac.app` | Привязка LO/HI к фактическому обработчику, кнопки REQUEST/CONFIRM, ограничения климата и жизненный цикл управления |
| `libbluetooth_jni.so`, `libbluetooth.so`, `EcarxBluetoothServiceExtension.apk` | Недостающий переход Java → native и правила подключения в службе расширения |
| Arm64 `libbluetooth-binder.so`, vendor `libbt-hidlclient.so`, `libbt-vendor.so`, `libbthost_if.so`, `libbtnv.so` | Продолжение той же native-цепи в нижележащих библиотеках |
| Settings, системные Adapt/Car JAR, выбранные установленные APK и их загруженные vendor-зависимости | Текущие версии и новые варианты относительно уже полученных файлов |
| Шесть точных файлов в `/ota_download/` | Манифест и пять пакетов `update-swp1/swl3/swl4/swlm/swl2.tar.gz`, если они остались после обновления; их наличие заранее не предполагается |
| Пять обычных файлов QNX | Сверка известных proxy/driver/version/LV image с текущим автомобилем через ранее подтверждённый qconn |
| Версия ГУ, сведения о выбранных пакетах, очищенные GATT-снимки | Связь новых файлов с текущим состоянием программного окружения |

`ts-dm-service.apk` уже найден и разобран в старом Cruise-архиве. Его повторная копия не является недостающим материалом: через PackageManager проверяется только текущий вариант, и известный SHA пропускается.

Для Android сначала читаются размер и SHA-256. При совпадении с базой известных файлов двоичные данные не передаются. Новый файл принимается только при совпадении скачанных размера и SHA с полученными метаданными. Повторяющееся содержимое внутри одного запуска хранится один раз, пути сохраняются в отчёте. Изменившиеся файлы отделяются от известных версий по хешу, а не по имени.

QNX не предоставляет используемому клиенту отдельный remote SHA-256: файл приходится прочитать, после чего известная копия удаляется. Клиент использует только файловую часть qconn через Android, точный адрес из сохранённых успешных трасс; `/dev/can*`, `/dev/spi*`, блочные устройства, запуск программ и команды автомобиля исключены. У qconn `stat` выполняется после открытия заранее проверенного пути обычного файла; предварительный `lstat` не обещается.

Каждый файл имеет предел размера, каждая команда — тайм-аут. Для одного OTA-пакета предел 2 GiB; при наличии нескольких новых пакетов результат может занять несколько гигабайт. Рабочая папка и итоговый сжатый архив сохраняются одновременно. Прогресс выводится по пакетам и файлам. Прервать сбор можно `Ctrl+C`: доступные результаты будут упакованы, незаконченный файл удалён.

## Содержимое результата

- `RESULT.json` — статусы каждой попытки и причины пропусков, версии сборщика и плана.
- `FILES.json` — размер и SHA-256 каждого сохранённого файла; сам манифест исключён из собственного списка.
- `COLLECTION_PLAN.json` — точный план этого запуска.
- `android/files/` и файлы с SHA-именами QNX — только новые полученные данные.
- `android/packages/`, `build.json`, `gatt_state.json`, `bluetooth_events.json` — выбранные метаданные и очищенные диагностические поля.

| Статус | Значение |
|---|---|
| `collected` | Полученные байты проверены |
| `known_duplicate` / `known_duplicate_discarded` | Этот SHA уже имеется; второй вариант статуса относится к чтению QNX с последующим удалением копии |
| `duplicate_in_run` / `duplicate_discarded` | То же содержимое уже получено в этом запуске |
| `missing` | Явный ответ об отсутствии; для условного OTA-пути это допустимый результат проверки |
| `permission_denied` | Файл не удалось прочитать с текущими правами; это не доказательство отсутствия |
| `timeout`, `unavailable`, `metadata_unavailable`, `changed_during_read` и другие ошибки | Достоверная копия не получена; причина сохранена |

`COMPLETED_COLLECTION_PLAN` означает завершение этого конечного плана. `PARTIAL` означает, что часть данных недоступна, пропущена или сбор остановлен. Оба архива нужны для следующего разбора. Коды выхода: 0 — план выполнен, 3 — частичный результат, 130 — прерывание. Параметры `--no-qnx` и `--no-bluetooth` оставляют явный пропуск и частичный результат.

Сырые HCI-пакеты, адреса Bluetooth, pairing keys, контакты, тексты звонков/уведомлений и приватные каталоги приложений не сохраняются. Bluetooth-текст обрабатывается в памяти по разрешённым форматам; неизвестные строки отбрасываются с подсчётом. Это ограниченная диагностическая выборка последних записей, а не полная запись будущего обрыва ANCS. Произвольные строки сторонних логов в отчёт не копируются. Архив с полученными системными бинарниками отправьте в этот разговор; согласно правилам проекта он не предназначен для публичного Git.

## Что пока нельзя получить таким сбором

Дисковый JAR или `/proc/PID/maps` не доказывает defining classloader конкретного Java-класса. Путь журналов `/data/kernellog/vp_*.log` установлен внутри Linux LV, но его доступный alias через текущие Android/QNX не установлен. Обработчик круиза в production ECU, аппаратные блокировки и физический STOP моторов также не становятся известны от наличия файла. Эти пробелы перечислены в плане отдельно; сборщик не подменяет их догадками или экспериментальными командами.

После получения архива следующий разбор начинается с `RESULT.json` и проверки `FILES.json`, затем разбирает только новые SHA: XCHvac, Bluetooth JNI/native/extension, изменившиеся SDK и компоненты обновления. Отказы доступа используются для уточнения конкретного следующего пути, а не для повторного запроса всех дампов.
