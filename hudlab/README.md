# HUD Lab

HUD Lab — отдельное диагностическое APK для физического ECARX HUD. Оно не входит в процесс
основного Status Widget. В версии 0.21 полностью удалены foreground service, boot receiver,
автоповтор и разрешения для их запуска.

## Экспорт трассы «крылья» 0.31

Во вкладке **«Приборка»** добавлена отдельная кнопка
`ЭКСПОРТ ЖУРНАЛА «КРЫЛЬЯ» В TXT`. Она экспортирует только полную трассу теста приборки:
состояния до/во время/после, ручную метку появления нижних блоков, ECARX/DIM,
task/window/displayId, WindowInsets, SurfaceFlinger и logcat. Общий журнал HUD-команд в
этот файл не подмешивается.

Основной путь открывает системное окно `ACTION_CREATE_DOCUMENT`, где можно выбрать папку и
имя TXT-файла. Если на автомобильной прошивке отсутствует системный выбор места, резервный
путь сохраняет файл в `Download/HudLabLogs`. После перезапуска HUD Lab можно экспортировать
последнюю сохранённую трассу, даже если новый тест ещё не запускался.

## Трасса приборки 0.30

Вкладка **«Приборка»** запускает только собственную зелёную Activity HUD Lab с текстовой
меткой. Навигационные приложения не запускаются и не останавливаются. Перед выводом
воспроизводится разобранная из DEX mNavi 2.0 последовательность:

1. если текущий `NaviMode == 3`, выполняется ограниченный reset
   `switchNaviMode(1) + DIM(2,8,8,[0])`;
2. через 500 мс отправляется `switchNaviMode(3) + DIM(2,8,8,[1])`;
3. ещё через 600 мс Activity запускается из ручной AccessibilityService с
   `ACTION_MAIN`, `FLAG_ACTIVITY_NEW_TASK`, `setLaunchDisplayId(2)`,
   `android.activity.SplitScreenShownPosition=0` и
   `android.activity.windowingMode=5`.

Служба специальных возможностей не читает содержимое окон, не работает при загрузке и не
повторяет команды. Она нужна только как тот же тип Context, из которого выполняет запуск
mNavi.

Для выяснения происхождения штатных нижних «крыльев» трасса снимает состояние до запуска,
несколько точек во время показа и состояние после закрытия:

- фактические `displayId`, task/window, размеры окна, `WindowInsets`,
  `ClusterActivityState` и multi-window;
- ECARX/DIM resource, priority и связанные сигналы приборки;
- имена и связанное состояние слоёв SurfaceFlinger;
- отфильтрованный системный logcat.

Изменения относительно исходного снимка помечаются `★`. Весь результат одновременно
сохраняется в `Android/data/dezz.status.hudlab29/files/cluster-traces/`; точный путь
показывается первой строкой журнала. Кнопка `★★ МЕТКА: НИЖНИЕ КРЫЛЬЯ ПОЯВИЛИСЬ` позволяет
снять дополнительный ECARX/window/SurfaceFlinger/logcat-срез ровно в визуально
подтверждённый момент появления штатных блоков.

## Одноразовый путь 0.21

Главная вкладка содержит две команды:

- `УБРАТЬ МАШИНКУ · MODE 2`;
- `ВЕРНУТЬ ШТАТНО · MODE 1`.

Одна кнопка выполняет одну конечную последовательность без фоновой работы:

1. записывает режим через ProfileTransfer `CB33278`;
2. отправляет прямой DIM `HudDispModSetgReq` (`signal30814`) с активным PEN;
3. формирует фронт `0→1` на `SaveSetgToMemPrmnt` (`signal29892`);
4. проверяет readback `PA33937`.

Если `ProfPenSts1` возвращает служебное `−1`, используется подтверждённый активный профиль
`PA33845` в допустимом диапазоне `0…13`. В полученном runtime это `PEN=13`.

## Шесть независимых способов в 0.21

На вкладке `ONE-SHOT` собраны шесть отдельных маршрутов:

1. **A — ProfileTransfer + DIM + SAVE:** одна конечная последовательность через
   `CB33278`, `signal30814`, `signal29892` и readback `PA33937`.
2. **B — UserProfile field 124:** точечная замена
   `profiletransferbyte3` (`CAR_FUNC_HUD_MODE`) внутри полного raw-профиля
   `PA33873 → CB33264`, с проверкой и точным откатом.
3. **C — прямой DIM:** одиночный `HudDispModSetgReq` (`signal30814`) для активного PEN,
   без ProfileTransfer и сохранения.
4. **D — visual mask:** ручной и ограниченный SAFE-поиск среди `F00…F19`
   (`signal30816`) с возвратом `all=1`.
5. **E — физический layer stack 2→22:** физический `local:2` на 12 секунд
   переключается со штатного stack 2 на тестовый stack 22, где создаётся зелёная
   контрольная поверхность. Возврат на stack 2 выполняется в `finally`; есть отдельная
   аварийная кнопка восстановления.
6. **F — Activity на displayId 2:** контрольная метка либо непрозрачный чёрный экран
   запускаются с теми же `displayId=2`, `windowingMode=5`, `splitPosition=1`, которые
   использует штатный `com.ecarx.hud`.

Способ E проверяет практический эквивалент идеи смены назначения HUD, но не переименовывает
логический `displayId` в `DisplayManager`: обычный APK не имеет системного setter для этого ID.
Если на новом stack видна зелёная метка без штатной машинки, гипотеза подтверждена. Если
машинка остаётся даже поверх E и F, её источник находится ниже Android-окон — в DIM/HWC либо
отдельном аппаратном слое.

## Исправления интерфейса 0.21

- результат последней команды постоянно виден над вкладками; `SUCCEED`, `PARAM_ERROR`,
  `not available` и локальная блокировка больше не выглядят как пустое нажатие;
- прямой DIM `HudDispModSetgReq` использует активный PEN из `ProfPenSts1`/PA33845 вместо
  ошибочно зафиксированного в 0.18 `PEN=1`;
- Navi status `4/5/6` больше не показаны как дополнительные HUD-режимы: native CB33267
  различает только `value==1` и сворачивает все остальные значения в один false-флаг;
- `DISPLAY_*` сохранены как диагностический маршрут, но больше не подписаны как рабочее
  скрытие: на исследованной прошивке функции не зарегистрированы и возвращают
  `notavailable / 255 / null`.

## Отдельные функции содержимого через `ICarFunction`

Во вкладке **«Элементы»** сохранён штатный маршрут ECARX Settings API через
`CarFunction.setFunctionValue(...)` для пяти объявленных функций HUD:

- `DISPLAY_DRIVE_ENVIRONMENT`;
- `DISPLAY_SAFETY`;
- `DISPLAY_MEDIA`;
- `DISPLAY_NAVI`;
- `DISPLAY_BTPHONE`.

Для каждой функции доступны только ручные `OFF/ON`, а для `DRIVE_ENVIRONMENT + SAFETY` —
совместная команда. Во вкладке **«Статус»** стенд отдельно показывает `support`, текущее
`value` и список допустимых значений, возвращённые SDK.

В исследованной прошивке эти идентификаторы присутствуют в `IHUD`, но HUD-модуль не
регистрирует соответствующие функции: фактический ответ устройства —
`not available` / `value=255` / `allowed=null`. Поэтому этот путь оставлен как
диагностический. Его отрицательный ответ не заменяется
вызовами через другой интерфейс `IHUD`.

## Старый штатный переключатель AR через профиль

Версия 0.21 повторяет точный путь удалённого из нового интерфейса пункта ECARX Settings
«AR режим». Функция `654443008` сериализуется в
`PA_PSET_ProfileCloudData.vfhudbyte0`. Стенд:

- получает активный `Profile ID` через уже подключённый PA33845;
- читает исходный protobuf целиком из PA33873 и требует все поля 1…150;
- синхронно сохраняет исходные raw-байты отдельно для каждого профиля;
- меняет только wire-поле 111 (`vfhudbyte0`) на `1` или `0`;
- передаёт исходный поток с этим точечным изменением через CB33264;
- ограниченно перечитывает PA33873 до подтверждения и показывает фактическое значение;
- кнопкой «ТОЧНЫЙ ОТКАТ» возвращает исходное значение AR поверх заново прочитанного полного
  профиля, не отменяя более поздние изменения сидений, климата, света и других настроек.

Публичный JSON намеренно не используется: AdaptAPI экспортирует лишь 85 из 150 vendor-полей и
при обратной записи мог бы обнулить остальные. Короткий, дублированный и all-zero raw-снимок
блокируется; неизвестные будущие поля выше 150 сохраняются байт-в-байт.

В 0.21 этот путь полностью убран из периодического обновления экрана. HUD Lab не загружает
`Car`/`IUserProfile` при старте и не читает PA33873 каждые 1,2 секунды. Проверка AR выполняется
только после явного нажатия «ПРОЧИТАТЬ AR», `AR ON`, `AR OFF` или «ТОЧНЫЙ ОТКАТ».

## RAW-проверка `CB33278 = -1` в версии 0.17

`ECarXCarProfiletransferManager.CB_HudDispModSetgReq(...)` проверяет
`DispModSetgReq.isValid(...)` и принимает только `0…3`. Поэтому обычный вызов с `-1`
возвращает `PARAM_ERROR`, не записывая ничего в CB33278.

Отдельная красная кнопка **«−1 RAW → CB33278 (В ОБХОД SDK)»** получает внутренний
ECARX property manager и выполняет прямую запись:

```text
setIntProperty(33278, VehicleArea_Global=1, -1)
```

RAW-команда разрешается только тогда, когда стенд уже сохранил валидный режим `0…3`.
Если PA33937 недоступен, успешная обычная команда `0…3` становится безопасной точкой возврата.
Кнопка **«ОТКАТ»** восстанавливает это значение обычным валидированным SDK-вызовом.
RAW-путь не входит в автоматический visual-mask цикл.

## Проверка visual mask

Разбор системного дампа подтвердил следующий путь:

- Android signal `30816` / VHAL `0x21707860`;
- IPCP service `0x26` (DIM), operation `27`, `SETREQUEST_NORETURN`;
- после разбора protobuf native-слой формирует IPCP payload ровно из 21 байта:
  `F00…F19`, затем `PEN`;
- IPCP подтверждает доставку кадра транспортным ACK, но отдельного
  функционального ответа, echo или getter применённой маски в Android-контуре нет;
- доказанный `ProfileId.isValid(...)` диапазон профилей — `0…13`.

Активный `PEN` определяется без предположений:

1. `getProfPenSts1()`, если значение находится в диапазоне `0…13`;
2. `getPA_PSET_ActiveProfile()` (`PA33845`), если первый сигнал недоступен или невалиден;
3. при отсутствии валидного значения команда не отправляется.

Кнопка **«Запустить полный цикл»** выполняет одну фиксированную последовательность на активном
профиле:

1. `all=0` на 3,6 секунды;
2. автоматическое восстановление `all=1` на 3,6 секунды;
3. двадцать проб `F00=0` … `F19=0`, каждый раз при всех остальных полях `1`;
4. обязательная финальная отправка `all=1`.

Каждая фактически отправленная команда записывается в журнал с полным вектором и
сериализованным protobuf. При штатном завершении, остановке, фиксации найденного `Fxx`, ошибке
или закрытии стенд отслеживает каждый профиль, на который успешно ушла неединичная маска, и
пытается восстановить `all=1` на всех таких профилях. Если `ecarxcar_service` оборвётся во
время пробы, цикл останавливается, а отложенное восстановление выполняется сразу после
переподключения. Пока автоматический SAFE‑цикл выполняется, все параллельные ручные
HUD‑записи отклоняются, чтобы они не могли изменить профиль, режим, активацию, тему или
вектор между шагами.

Низкоуровневая вкладка позволяет вручную выбрать только `PEN 0…13`. Значения вне
подтверждённого диапазона отклоняются до обращения к vendor API.

```sh
./gradlew :hudlab:testDebugUnitTest :hudlab:assembleDebug
```

Готовый APK создаётся в `hudlab/build/outputs/apk/debug/`.
