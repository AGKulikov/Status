# Status Widget v2.8.2-ha1210 — Pie opportunistic reverse ANCS attach

Paired Android/Helper transport follow-up to HA1209 for the Geely Monjaro/KX11 Android 9 head
unit. Launcher first-frame atomicity and the low-contention boot lanes from HA1209 are unchanged.
The matched iPhone component is Helper v44 (build 44, marketing 44.0, bundle
`ru.natro.kx11ancshelper`) and is compiled by the separate macOS `verify-helper-v44.yml` gate.
The preserved HA1209 inbound transcript still resolves wrapper churn through one stable `GattServerPeer`;
raw PAIR facade ownership remains identity-strict for the reverse client role.

## Root cause confirmed

The HA1209 field trace completes the exact reverse PAIR -> B3 status 5 -> encrypted B3 ->
same-owner ANCS-READY transcript. Android then calls the documented direct
`connectGatt(autoConnect=false)` overload three times against the existing iPhone-Central link,
but ECARX Android 9 allocates no callback. Repeating a normal virtual open can compete with the
only working inbound GATT-server/ACL owner and is therefore not a safe adoption mechanism.

## HA1210 Android behavior

- The checked ANCS-READY ATT response remains the command barrier. No client-role close, open,
  discovery, RSSI or reconnect command can run before the exact current session, security epoch,
  F04 publication and raw PAIR facade tuple passes that barrier.
- The captured task invokes the Android 9 light-greylist `BluetoothDevice.connectGatt` overload by
  reflection with `autoConnect=false`, `opportunistic=true`, `TRANSPORT_LE`,
  `PHY_LE_1M_MASK` and the transport main handler. On AOSP Pie, `autoConnect=true` selects the
  background path before the opportunistic flag is applied, so it is deliberately not used here.
- The registration is exact-live-link-gated and non-holding once bound. There is still a narrow
  Bluetooth-main race: if the native TCB disappears after the Java server-link check but before
  queued `GATT_Connect`, the opportunistic direct request can transiently initiate. The one-call
  budget, lack of fallback and independent server-DISCONNECTED retirement bound that residual.
- Exactly one opportunistic registration is permitted per exact PAIR/B3/READY tuple. There is no
  documented-public `connectGatt` fallback and no attempt #2/#3 after reflection failure, null,
  exception, callback error, disconnect or timeout.
- A silent never-established wrapper is unregistered with `BluetoothGatt.close()` only after the
  exact attempt lineage check. HA1210 never calls `BluetoothGatt.disconnect()` for an
  opportunistic wrapper and never closes the inbound GATT server or advertising publication.
- A client-only failure consumes the tuple budget but preserves the still-current inbound server
  peer, PAIR/B3/READY proof and F04 publication. Only an independent server-facade DISCONNECTED
  event proves physical loss and opens a fresh epoch.
- An established opportunistic observer cannot enter `awaitIncomingBackgroundOwner`,
  `rearmPersistentGattOwner` or `BluetoothGatt.connect()`. A fresh incoming epoch close-only
  retires the old observer before clearing the tuple, then permits one new post-READY attempt.
- Because the hidden overload already delivers on the transport main handler, all seven shared
  GATT callbacks commit inline when already on that looper; legacy off-main callbacks make exactly
  one handler hop. A stack completion queued before its connect, discovery, descriptor, read,
  write or RSSI watchdog therefore cancels that watchdog before it can close/poison the owner.
- Runtime diagnostics include `HA1210 Pie opportunistic reverse attach enabled` and every hidden
  invocation records `autoConnect=false, opportunistic=true` for deterministic field validation.

## Matched Helper v44 behavior

- A Core Bluetooth-restored exact owner that remains system-owned `.connecting` may adopt one
  strictly newer fixed-generation protocol-2 Android publication nonce without a manual tap.
- Before the one cancel/reopen, Helper durably commits the exact `(owner, nonce)` tuple. A crash,
  restoration repeat or replay of that tuple therefore cannot create another reopen.
- Protocol-v1 frames and same/older protocol-2 nonces are read-only. They cannot consume the v44
  adoption budget or supersede the ordinary v43 token-bound recovery rules.
- Bundle ID, Core Bluetooth restoration identifiers, saved Geely identity and the system
  Classic/LE pair remain unchanged for an in-place Helper upgrade.
