# Status Widget HA1192 + iPhone Helper v30

Package: `ru.natro.statuswidget`

Version name: `v2.8.2-ha1192`

Version code: `208021192`

## Reproduced Central-route failures

- In both 17:58 and 18:53 traces, the second B3 read succeeded with `SECURE ATT OK`, but the
  immediately following `ANCS-HANDOFF` write failed with `CBATTErrorDomain:5`. Phase two never
  started; there was no accepted handoff, `ANCS-READY`, ANCS CCCD proof, or B4 subscriber.
- Android committed `secureAttConfirmed` only later on its main thread, after returning the B3
  success from a Binder callback. The handoff write could therefore observe a stale false value.
- Android also called `createBond()` from an anonymous incoming callback before Helper sent
  `PAIR`. In the 18:55 attempt that churn coincided with repeated `CBErrorDomain:8` characteristic
  discovery failures.

## Matched-pair fix

- Android commits the verified B3 proof synchronously before returning `SECURE ATT OK`; the next
  handoff write cannot race the proof.
- Anonymous `didConnect` callbacks never initiate bonding. LE security begins only after the
  verified `PAIR` command and the bounded B3 authentication challenge.
- Helper v30 uses new Core Bluetooth restoration identifiers. If one ATT owner reports
  `uuidNotAllowed`, it is released once so Android can advertise a new dynamic namespace; Helper
  does not repeat the same prohibited discovery call.
- Green is a three-part assertion: both ANCS CCCDs succeeded, Android actually parsed a valid B4
  telemetry payload, and Helper acknowledged `ANCS-SUBSCRIBED`. The proof write is retried on the
  live owner after a transient failure or timeout.
- Android no longer publishes `ANCS READY` to the controller after CCCD setup alone. Until the B4
  payload and its acknowledged proof arrive, the visible state remains `ANCS CCCD OK · ЖДУ B4`.

## Protocol basis

- Apple defines the iPhone as the ANCS Notification Provider and the accessory as the GATT client;
  the Android side therefore remains the ANCS client after the iPhone opens the
  `CBConnectPeripheralOptionRequiresANCS` link.
- The ANCS service contains Notification Source, Control Point, and Data Source; all require
  authorization. Battery and cellular-network type are not ANCS attributes, so Helper publishes
  them independently in the B4 telemetry relay.
- Helper declares both `bluetooth-central` and `bluetooth-peripheral` background modes and uses
  distinct restoration identifiers for those two Core Bluetooth managers.

## Retest

1. Install HA1192 and Helper v30 as one matched pair; select **Central** in both.
2. Wait for `ANCS-HANDOFF accepted`, `ANCS-READY accepted`, a B4 read with battery/network values,
   and finally green `ANCS + ТЕЛЕМЕТРИЯ АКТИВНЫ`.
3. Verify a battery-percent/network change and send a new, non-pre-existing notification.
4. For limiter capture, start a fresh action session immediately before one distinct limiter
   action and stop it immediately afterward.

Classic Bluetooth profiles, names, pairing records, vehicle settings, and controls are not
deleted or reset by this release. LE security starts only after the verified PAIR/B3 exchange.
