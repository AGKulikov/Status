# Status Widget v2.8.2-ha1215 + iPhone Helper v49 — unified Classic/ANCS candidate

HA1215 turns the field-proven single-iPhone topology into an explicit production policy. The
selected system bond remains the only logical phone identity: ECARX keeps HFP/A2DP/PBAP on
BR/EDR, while Route A adds one LE GATT link carrying both Apple ANCS and Helper telemetry. These
are two physical Bluetooth transports, but they must resolve to one selected phone and one UI
entry. Route B remains available only as an explicit diagnostic experiment and is never started
concurrently or used as a silent fallback.

## Classic-connected ANCS acquisition

- Android is authoritative for the exact selected Classic profile state. A live selected HFP,
  A2DP or MAP profile without ANCS is a degraded session rather than a successful terminal state.
- A degraded session starts Route A immediately. Confirmed owner/link loss uses bounded fast
  same-role recovery followed by bounded backoff while Classic remains connected; it never gives
  up permanently merely because the first attempts failed.
- A live encrypted GATT owner waiting for dynamic ANCS publication with Generic Attribute Service
  Changed armed is preserved. It is not replaced by a polling or reconnect storm.
- Every real replacement uses the existing full same-role drain, owner-zero proof and fresh
  epoch/generation. Late callbacks from a retired generation cannot mutate the successor.
- The exact selected system-bond address is mandatory. A different facade/RPA, a second bonded
  peer, an ambiguous owner or a Helper installation-identity conflict fails closed and cannot
  create or overwrite a phone identity.

## Helper v49 production behavior

- Route A owns one restorable `CBPeripheralManager`, advertises only the fixed F201 service UUID,
  and publishes no local name or secondary pairing identity.
- With no authenticated Android owner the Helper stays locally available/restorable. Android,
  which can observe Classic profiles, decides when the missing ANCS link must be actively
  acquired.
- Telemetry and route control remain fenced to the exact encrypted owner. A real disconnect or
  terminal failure escalates through the existing same-role drain and a fresh generation; a live
  owner waiting for ANCS is not churned.
- Route B remains diagnostic and uses its own manager/restoration namespace. Both routes can never
  own Core Bluetooth resources at the same time.

## Safety barriers

- No bond creation/deletion, adapter toggle, Bluetooth service restart, global GATT-cache refresh,
  profile disconnect or vehicle write is used for recovery.
- The unrelated GPS BLE sensor is neither disconnected nor reconnected by this policy.
- ECARX/nFore remains the owner of Classic profiles and audio routing. HA1215 calls only the exact
  existing selected-phone connect path; the OEM method named `reqBtPair` maps to the vendor
  `requestConnect` implementation and never receives a BLE/RPA address.
- ANCS authorization remains an iOS system decision. Denial is reported as actionable degraded
  status and is never bypassed.

## Public implementation evidence

The normative mapping is recorded in `docs/ANCS_V2_REFERENCE_ARCHITECTURE.md`. Nordic, BTstack,
ESP-IDF, `Androdi-testANCSDemo` and `ultra` all establish LE before consuming ANCS; none proves an
ANCS-over-Classic bearer. `bridgething` supports the Helper-central/`RequiresANCS` topology but is
a Linux accessory, not Android 9. HA1215 therefore promotes the already observed public-API Route
A and leaves Android 9's hidden reverse-observer Route B experimental.

## Read-only KX11 collector

`tools/KX11_Bluetooth_Collect.command` creates a private local archive of Bluetooth configuration,
package paths, dumpsys output and logs. It never remounts or writes the head unit, never toggles
Bluetooth and never clears pairing/cache state. `--root` only restarts adbd to read protected
diagnostic files. Raw output can contain device addresses and Bluetooth keys and must not be
published unredacted.

## Hosted exact-byte gate

Workflows: `.github/workflows/verify-ha1215.yml` and
`.github/workflows/verify-helper-v49.yml`. They must run the complete geely unit suite, portable
Helper contracts, unsigned Android release build, unsigned iPhone-simulator build, package/version
checks and exact-source packaging on one committed snapshot. The Android APK is then signed
offline with the established update certificate without rebuilding or realigning it.

## Physical KX11/iPhone acceptance still required

HA1215 remains a candidate until the signed apps pass, with the GPS BLE sensor left connected:

- at least 30 cold-start and out-of-range/return cycles with one bonded/UI iPhone entry;
- Classic-first, LE-first, Bluetooth radio off/on, Helper relaunch, Android process restart and
  update-over-HA1214/v48;
- HFP call audio, A2DP music, PBAP/MAP and a fresh real ANCS notification after every recovery;
- one LE owner containing both Helper F201 and ANCS, no overlapping route or GATT owners, no stale
  notification UID/telemetry after a generation change, and no GPS disconnect caused by recovery;
- bounded degraded/recovery status and recovery latency recorded separately for authorization
  denial, Service-Changed waiting, real link loss and identity rejection.

Hosted reducer/source/build checks cannot substitute for those radio, iOS authorization and ECARX
audio-routing observations.
