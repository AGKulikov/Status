# Status Widget v2.8.2-ha1202 + KX11 ANCS Helper v39

Matched recovery build for the Geely Monjaro/KX11 Android 9 head unit and iPhone.

## Root causes proved by the 2026-08-09 13:17 logs

- HA1201 registered Android's reverse GATT client four milliseconds before the asynchronous F04
  `onServiceAdded(SUCCESS)` callback. On this ECARX Android 9 stack that first premature clientIf
  never produced a connection callback and also poisoned the following wrapper until the BLE
  controller was restarted.
- After a clean restart, direct client attachment succeeded and the exact owner passed PAIR and
  encrypted B3. Helper v38 then suppressed `ANCS-READY` because the immediate
  `CBPeripheral.ancsAuthorized` snapshot was false, while Android deliberately waited for READY
  before real ANCS discovery. Both sides therefore waited forever.
- A restored request could also reach the physical F04 link without delivering `didConnect`; the
  first rescue path did not arm its bounded second ownership reconciliation in every terminal
  callback order.

## HA1202 Android transport

- The exact bonded incoming owner may be retained immediately, but no reverse `connectGatt`, PAIR,
  B3, READY mutation or service discovery is allowed until the current GATT-server publication
  receives `onServiceAdded(SUCCESS)` for the exact pending F04 service object and lifecycle token.
- A late callback belonging to a closed server publication cannot open the barrier. The barrier is
  invalidated on every close, reset and failed publication, before any subsequent callback can be
  accepted.
- Successful current publication resumes one idempotent direct attach without consuming an
  attempt beforehand. Existing security-epoch, client-generation and current-publication gates
  remain mandatory before discovery.
- Mandatory ANCS descriptor writes are owned by the exact descriptor, wrapper, client generation,
  security epoch and publication token. A missing callback closes that ambiguous wrapper; at most
  one replacement is allowed on an exact still-connected F04 facade, and a second consecutive
  timeout waits for a new physical link instead of looping. A real status 133 callback receives
  one bounded same-owner retry and can never mark ANCS ready.
- Service discovery is also a single exact operation owned by its GATT wrapper, client generation,
  security epoch and F04 publication token. Abandoning or timing out a raw discovery/descriptor
  callback slot closes that wrapper before a new epoch may start, so a late callback can never be
  reinterpreted as the result of a successor operation on Android 9.
- F05/B4 server-side subscription and telemetry callbacks are accepted only for the exact current
  F04 publication object and token, with the same lineage rechecked where the callback is posted;
  callbacks queued before a stop/republication cannot mutate the new session.
- ANCS privacy is decided by the real Notification Source and Data Source CCCD callbacks. A
  denied/pending status keeps the physical link and reports the user action without polling the
  GATT database or rotating identity.

## Helper v39

- `ANCS-READY` now means one exact RequiresANCS owner passed encrypted B3. It is written exactly
  once after B3 even when the early Core Bluetooth authorization snapshot is still false.
- Green readiness is callback-driven: the current owner must be connected, B3/READY must be
  complete, Android must report both real ANCS CCCDs through current F05/B4 proof, B4 must be
  subscribed and valid telemetry must be present. A later explicit authorization denial
  invalidates the current ANCS proof but never tears down the link.
- A real non-system disconnect materializes one exact-owner deferred connect. A matching late
  `didConnect` consumes that intent atomically; `isReconnecting=true` remains wholly system-owned.
- Restoration has a hard two-claim limit. The second claim requires the same saved identifier in
  Core Bluetooth's F04 connected-peripheral table; advertisements and elapsed time are never
  treated as proof of a connected ACL. Every terminal order arms the same bounded recovery path.
- A live B4 subscription restored after process eviction is accepted only through a two-sided,
  one-shot proof: the exact persisted Central owner must be restored already connected and the
  exact restored F05 characteristic must list that same owner in `subscribedCentrals`. Fresh
  connects always start B4 readiness false; either restored hint still requires B3/READY and a
  new current Android `ANCS-SUBSCRIBED` proof before green.
- Helper's own F05 publication has an exact pending/published service identity and monotonic
  generation. A late `didAdd` from a removed publication is logging-only and cannot publish,
  remove, advertise or start the Central route for the replacement service.
