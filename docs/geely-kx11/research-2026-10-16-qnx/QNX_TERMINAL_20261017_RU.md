## Непосредственно видно на экране

```text
connect
Connected · 127.0.0.1:5555
toybox nc -w 30 198.18.34.2 8000
nc: connect: Connection refused
Код завершения: 1
```

Строка Connected относится к локальному ADB endpoint 127.0.0.1:5555,
а не к QNX 198.18.34.2:8000. Приветствия QCONN в выводе нет.

Контроль прежней команды через обычный терминал выполнен: тот же отказ
наблюдается без вызова collectInventory/qnxStage и файловых запросов QNX.
Значит, ошибка воспроизводится не только при новом обходе каталога.
Она не сводится к qnx_bad_line в сборщике: сама nc возвращает отказ и код 1.

Это не полное оправдание любых изменений приложения: терминал использует
Natro/ADB, предыдущие действия и точная непрерывность сеанса неизвестны.
Не доказаны остановка qconn, изменение порта, неверный маршрут, firewall
reject либо косвенное последствие прежнего запуска. Недоступность этого
TCP endpoint не означает неработоспособность QNX целиком.

## Следующий минимальный read-only шаг

В том же обычном терминале, без переключения сети и перезагрузки,
выполнить по отдельности и сохранить весь вывод:

```sh
ip route get 198.18.34.2
```

```sh
ip neigh show 198.18.34.2
```

Первый результат нужен для текущих interface/source/table; второй — для
имеющейся записи соседа. Это команды просмотра, не изменения настроек.
Пустой вывод neigh не означает автоматически отключённый QNX. Даже
наличие соседа и похожего маршрута не доказывает доступность порта 8000.

При отличии маршрута от исторического сначала установить его причину;
не подменять диагностику принудительной сменой маршрутов. При согласованном
маршруте следующий пробел — read-only свидетельства службы и возможного
активного сетевого отклонения; способ сбора выбрать после текущего вывода.
Повторное произвольное ожидание, запуск демонов, изменение firewall,
перезапуск QNX и переустановка с удалением данных не назначаются.

проверьте её фактический результат». Обе последующие ip-команды получили

Это не повторный Connection refused и не доказательство остановки adbd.

IMG_8797: после нового connect обе ip-команды завершились кодом 0:
`198.18.34.2 dev eth0 table ecarx_ap_vp_route src 198.18.34.15 uid 2000`, cache.
Запись соседа на eth0: `lladdr 02:00:00:00:12:02 REACHABLE`.
На eth0.3/.2/.6/.5/.4/.11 виден тот же MAC, состояния REACHABLE/STALE.
Маршрут совпадает с историческим успешным по этим полям; наблюдаемого ухода
через другой интерфейс нет. ARP/neighbor не проверяет TCP listener 8000,
не исключает фильтрацию и не устанавливает состояние службы qconn.

SOURCE-аудит опубликованной ветки 78cd5ea:
AdbConsoleModel вызывает s.command(command), затем отображает result.describe();
AdbConsoleSession.captureCommand копит вывод, а при исключении отключает
transport и не возвращает capture.finish(). Обычный submit имеет 60 секунд,
cancel закрывает socket, finally disconnect обнуляет transport.
Поэтому отключение после таймаута объясняется собственной логикой Natro,
а полученные до ошибки байты могли не попасть на экран. Их наличие,
приветствие QCONN и причина ожидания этим фото НЕ доказаны.
Локальные файлы совпали с удалёнными Git blobs:
AdbConsoleModel ba45d4027a8c5eab1bfc5189b43576c5068f29c6;
AdbConsoleSession e1dd7c7414ff3ec358b1b199ad1ffb8a3e19676e;
shell/AdbTransport a03a114040cf9aa3c8ddf2fa4e55f5831e926ab6.

Поправка к прежней инструкции: -w 30 не следует выдавать за общий предел
времени nc. В проверенном исходнике Toybox -w ограничивает установление
соединения; после успешного connect этот таймер снимается:
https://android.googlesource.com/platform/external/toybox/+/7aa651a6a4496d848f86de9b1e6b3a003256a01f/toys/other/netcat.c
Это первичный исходник, но не подтверждение точной vendor-сборки Toybox
на данном HU; её help/бинарник пока не получены.

Следующий однократный контроль в восстановленном терминале:
```sh
toybox timeout 5 toybox nc -w 3 198.18.34.2 8000
```
Внешний timeout ограничивает именно диагностический дочерний процесс,
не запускает/не останавливает службу QNX и не меняет настройки.
Доступность applet timeout в конкретной vendor-сборке ещё не проверена:
если Unknown command/usage — сохранить ошибку, не возвращаться к
неограниченному nc. Нужен весь вывод, включая возможный QCONN и exit code.
Срабатывание внешнего timeout само по себе не означает отказ соединения.
При новом 60-секундном таймауте прекратить повторения и разбирать
исполнение/потерю вывода Natro по прикладным логам.

Текущий next step заменяет уже выполненную route/neigh проверку выше.
FIELD маршрута/neighbor получен; текущий TCP/QCONN после восстановления
ADB не проверен, первопричина OPEN. Начальный Connection refused остаётся
валидным отдельным наблюдением; эти фото не отменяют его и не объясняют
его причину. Полный QNX сбор BLOCKED_TRANSPORT. Код и APK не менялись.
