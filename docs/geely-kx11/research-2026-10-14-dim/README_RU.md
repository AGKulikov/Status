## Точная привязка Android UART

Свежий uart-context показывает:

- `/sys/class/tty/ttyHS2/device` → `/sys/devices/platform/soc/890000.qcom,qup_uart`;
- `DRIVER=msm_geni_serial`;
- `OF_FULLNAME=/soc/qcom,qup_uart@0x890000`.

Таким образом, ttyHS2 относится к контроллеру 0x890000, названному QUP4 в
linux.config. Прежний пробел в нумерации Linux закрыт наблюдаемым sysfs.
QNX startup запускает этот контроллер для ser4, а конфигурация VM отдаёт его
Android через passthrough. Это согласуется с последовательной настройкой при
старте, но не доказывает, что QNX является принимающей стороной UART или кто
владеет портом в каждый момент. Физический внешний endpoint пока не установлен.

## MAX96755_QC_0: что делает найденный поток

Адреса ниже — виртуальные адреса внутри именно ELF с хешем из таблицы.
Метод: AArch64 disassembly, ELF symbols и relocation/PLT, ссылки на строки и
данные; не только поиск текстовых совпадений.

| Участок | Проверенное действие |
|---|---|
| Panel_Init 0x24f8, вызов 0x2a60 | Создаёт поток 0x2b10. |
| 0x2b10…0x2cd8 | Читает /etc/system/config/variant.cfg, выбирает вариант, вызывает configure_dsi0_displays. |
| configure_dsi0_displays 0x4d08 | Создаёт worker 0x44fc и ждёт его pthread_join в 0x4dd0. |
| worker 0x44fc, open 0x45a4 | Открывает /dev/ser4, задаёт 115200 через termios. |
| write 0x4784, read 0x4824 | Посылает запрос идентификации сериализатора, читает до 12 байтов ответа, проверяет начальный 0xc3. |
| 0x48ec…0x48f8 | Для KX11_HIGH/MID выбирает dim_high_init, шесть записей. |
| 0x49a4…0x49b0 | Для KX11_LOW выбирает dim_low_init, двадцать записей. |
| helper 0x3e58 | Записывает ограниченную таблицу команд, читает ACK, ограничивает повторы. |
| close 0x4c08, pthread_exit 0x4c64 | Закрывает ser4; пишет диагностическое сообщение о завершении DIM-потока и завершает его. |

Строки variant.cfg отображаются так: EX11_LOW→0, EX11_HIGH→1, KX11_HIGH→2,
KX11_MID→3, KX11_LOW→4, CX11_HIGH→5, CX11_LOW→6, неизвестный→7.
Фактический variant.cfg текущей машины в этом дампе отсутствует: название
машины не заменяет чтение файла.

dim_high_init (0x182a0, 96 байтов) состоит из шести 16-байтовых записей с
6-байтовой командой, длиной и параметром повторов. SHA256 таблицы:
`284d7743d563d8be92e6e7efe6cdf0c9b0981b63378d6caaacb7b59f2c6b2ea8`.
Команды настройки сериализатора соответствуют уже описанному DIM_init
Android-драйвера; это подтверждение общей инициализации, а не новый флаг крыльев.
dim_low_init (0x18160, 320 байтов), SHA256
`b38bd9ff5cd8f9b058e7ab58e6fddb1f2f21e4cd4d1e39545655e34599670a15`,
относится к другому варианту оборудования. Переключать таблицы ради оформления
приборки оснований нет.

Исследованный поток — ограниченная инициализация видеосериализатора. Он не
остаётся постоянным диспетчером навигационных пакетов после запуска. В нём
не найдено управление отдельными «крыльями». Это не отрицательное доказательство
для всех процессов QNX, прошивки внешнего DIM или всех режимов panel library.
Смежные MAX96755_1/DP_COMMON также просмотрены как источники портов и init-кода;
полного доказательства отсутствия renderer во всей QNX-системе нет.

## Что нужно дальше

1. В read-only снимке уточнить variant.cfg и разрешение /lib64 для фактически
   загруженной panel library; сопоставить с запуском devc-quipv3 и passthrough.
2. Искать в имеющихся firmware inventories именно прошивку внешнего DIM/
   видеоприёмника и её идентификатор. MCU A с другим SPI-протоколом из прежнего
   разбора не объявлять нужным получателем по одному слову DIM.
3. Найти вызываемый принимающий dispatcher навигационных команд и отдельный
   параметр оформления с сохранением карты. Только после этого возможен
   проверяемый патч. Выключение всего навигационного режима этой задачи не решает.

Статус: транспорт уточнён, init-поток прослежен; receiver и физическое отключение
«крыльев» остаются OPEN. Никакие таблицы, firmware или команды DIM не изменены.
