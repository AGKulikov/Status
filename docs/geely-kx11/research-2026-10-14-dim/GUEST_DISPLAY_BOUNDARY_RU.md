## wfd_be: проверенная ветвь транспорта

main0x2960 принимает числовой client type из argv[1] через atoi0x2ad8;
в help имеются типы1..7, в том числе5 LA_GVM и6 LV_GVM. В текущем inventory
два процесса wfd_be, но exefile не содержит argv: назначать им5/6 по одному
порядку PID нельзя. Бинарник не запускался даже для help.

Приём habmm_socket_recv0x3220; затем:

- 0x3260..0x3270 проверяет magic0x64697370;
- 0x328c..0x3294 проверяет поле типа0/1;
- ветвь типа0 проверяет значение0x04010000;
- selector по0x32cc ограничен0..46;
- 0x32f0..0x3304 выбирает указатель из таблицы0x18008 и вызывает handler.

Таблица восстановлена из ELF relocations, а не предположена по строкам.
Handler8 0x47f0 вызывает wfdEnumeratePorts; handler9 0x48c4 — wfdCreatePort.
Handler33 0x4fec передаёт device/pipeline/attribute/value в
wfdSetPipelineAttribi;34 передаёт float;35 — vector int.
Это графический RPC, не найденный UART приёмник opcode14/8.

**Handler44 0x5b44 и45 0x5b4c состоят из mov w0,0; ret.** Они не заполняют
результат. Нельзя считать нулевой возврат содержательной диагностикой или
ожидать от этого guest backend тот же composition API, что есть в прямом
QNX openwfd_server. Тождество имён handler44 между двумя ABI само по себе
не доказано; установлены именно индекс и пустое тело в данном backend.
Прямой server query по-прежнему требует отдельного client type/driver lock
и не включается в пассивный сбор.

## Дополнительная проверка libkx11_lib

Get_ADAS_Obj0x1c304 вызывает Draw_Obj_new и копирует числовые поля в выходные
указатели; Get_ADAS_LD0x1c868 вызывает Draw_LD и копирует числовые поля полос.
Это расширяет проверку за пределы NAVI, но не является полным разбором каждой
функции. В этих проверенных API framebuffer или самостоятельный display output
не обнаружен. Связь с DIM wings не доказана.

## Что осталось различить

1. Крылья уже являются пикселями Android кадра DIM+HUD.
2. Они добавляются после этого кадра, в том числе во внешнем DIM.
3. Иной runtime источник/маршрут, не отражённый текущей XML-конфигурацией.

Вариант единого слоя с прозрачной серединой совместим с этим разбором.
Нет основания менять alpha всего layer16: это может затронуть весь DIM+HUD.
Нужна привязка физических пикселей к синхронной композиции/снимку источника,
а не очередное сопоставление имён слоёв или номеров из разных доменов.
