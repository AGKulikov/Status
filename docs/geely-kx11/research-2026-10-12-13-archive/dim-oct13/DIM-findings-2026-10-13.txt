1. Что найдено раньше и перепроверено
DIMProtocolService -> vendor.ecarx.xma.dimprotocol@1.0-service -> libuart.so
-> write(/dev/ttydim0). Это подтверждённая Android-сторона транспорта,
но не окончательный обработчик на стороне приборки.

switchNaviMode локально принимает OFF=1, SIMPLIFY=2, FULL=3, AR=4.
Для OFF/SIMPLIFY отправляется opcode14, msgType0, len8, API data=[2].
Для FULL/AR — те же поля и API data=[1].
Один байт API не означает, что все восемь байтов на линии являются
независимыми параметрами. В захвате остальные семь равны нулю.
NaviInteraction.updateExtensionInfo во всех четырёх ветках режима
отправляет opcode8,msgType2,len8,data=[1]. Это не четыре разных кода режима.

2. Новое уточнение обратного пути
NaviInteraction$DIMProtocolServiceCallbackImpl.onReceived:
opcode != 7 -> здесь ничего не делает.
opcode7, data2 -> onDoInteractionAction(33,null): выход из fullscreen.
opcode7, data1 -> читает getNaviMode:
  локальный FULL=3 -> onDoInteractionAction(35,null);
  локальный AR=4 -> onDoInteractionAction(36,null);
  другие локальные режимы -> этих действий нет.
Следовательно FULL/AR различаются и локальным состоянием Android,
хотя байт запроса14 у них одинаковый. Один RX7 data1 сам по себе не
определяет, какой Android callback будет вызван.
Доказательство: dim-menu.disasm.txt, класс NaviInteraction$DIMProtocolServiceCallbackImpl,
onReceived offsets 0x00..0xc4.

3. Возврат switchNaviMode не является ACK
DimMenuInteraction.switchNaviMode после вызова sendMessageToDIM возвращает
константу true (offsets 0x138..0x13a). Ожидания ответа DIM в методе нет.
Даже ветвь неизвестного номера режима только логирует его и идёт к true
через 0x80; это не означает, что при исключении тоже возвращается true.
Успешный возврат нельзя считать доказательством изменения изображения.

4. Локальная синхронизация DimMenu
DimRepository.switchFullMode устанавливает IS_USER_ACTION=true.
syncNavigationMode при IS_USER_ACTION=true немедленно возвращается.
Иначе Settings.System.display_on_dashboard == "normal" выбирает режим3;
другое значение — режим1. Значит одного изменения сохранённой строки
недостаточно гарантировать синхронизацию через этот метод.
Когда/кто сбрасывает IS_USER_ACTION, в данном неполном наборе классов
ещё не прослежено. Это не доказательство конкретного сбоя Natro.

5. Перепроверка кадров
Для каждого полного кадра CRC32 вычислен заново по байтам от magic до
конца payload; сохранённый CRC — big endian. Не использовался готовый
флаг crc_ok как доказательство.
В переходе 10.08 все6 кадров корректны:
TX14 -> +75мс RX ACK14 -> +103мс TX8 -> +176мс RX ACK8
-> +276мс RX7 data1 -> +277мс TX ACK7.
Это один захват, не нормативные тайминги.
В восстановленном фрагменте ядра 13.08: 511 записей, 507 полных с верным
CRC, четыре обрезаны до окончания CRC. Обрезанные записи не доказывают
порчу кадров на линии.
Все6 TX14 корректны: три data02 через200мс, затем три data1c примерно
через200мс. Между первой02 и первой1c —604мс. Причина смены байта
не установлена: нет вызывающего API в этом фрагменте. 0x1c не объявляется
новым режимом или параметром крыльев. Повторяемость не доказывает ACK/retry
механизм без корреляции с отправителем.

6. Другие найденные сообщения SDK, не команды крыльев
notifyDimControlCenterActiveType: opcode15,type2,data=byte(activeType).
notifyDimEnterControlCenter: opcode18,type2,data=byte(input).
setVolume: opcode10,type2,data=byte(volume); перегрузка с mute добавляет100
к volume перед преобразованием в byte, когда mute=true.
notifyIHUReady: opcode1,type2,data1; дополнительно opcode19 для wallpaper1..3.
Названия и значения относятся к разобранному SDK. Не предлагается
посылать эти сообщения вручную; визуальные эффекты не проверялись.

7. Что НЕ найдено
Независимый visibility/height/координаты крыльев и конечный renderer.
Искомый нижний драйвер /vendor/lib/modules/dim_dtc.ko ранее отсутствовал
в разобранных экспортированных материалах. Поиск названия dim_dtc и
DIM-receiver среди загруженных пользователем файлов сейчас не дал
совпадений; это не проверка содержимого всех архивов.
Нельзя утверждать, что драйвер сам рисует крылья: это звено транспорта,
а графика может обрабатываться дальше на другой стороне.
Соседство ttydim0/max9675x/ttyHS2 в журналах не доказывает прямое отображение
устройств. Нужен код драйвера/принимающей стороны или трасса её обработки.
Пояснение пользователя о заранее заданных фигурах круглых шкал сохранено:
они не считаются доказательством раннего появления штатных крыльев.

Итог: механизм запроса режима и Android-реакции существенно раскрыт.
Безопасное независимое скрытие крыльев пока не найдено. Переключение
FULL/OFF затрагивает весь режим и не эквивалентно настройке крыльев.
