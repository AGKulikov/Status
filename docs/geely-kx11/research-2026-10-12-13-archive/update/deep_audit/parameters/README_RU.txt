ПАРАМЕТРЫ И СВЯЗИ XCSettings2 — продолжение 13.10.2026

Это статический разбор предоставленного update, без запуска APK, native-библиотек,
сценариев установки, обращения к машине или внешним сервисам.

ЧТО ДОБАВЛЕНО
1. UI_PARAMETERS_RU.txt / ui_parameters.json — 150 пар type/id из всех уже
   извлечённых JSON-экранов, включая 139 типизированных. Сохранены названия,
   варианты выбора по локалям, defaultValue, stored, страницы, пути ресурсов.
   defaultValue из JSON не равен текущей настройке конкретного автомобиля.
2. ui_parameter_branch_candidates.json — 2106 специализированных сценариев
   для 42 объявленных методов обработчиков. Включены переключатели, индексы,
   чтение, доступность и rollback. Есть отдельно найденные программные ID.
   Это возможные обращения по статическому CFG, не проверенные команды машине.
   Пробы индексов 0..7 НЕ задают допустимый диапазон. Неизвестные runtime-ветки
   объединяются; наследуемые методы не разворачиваются автоматически; float-
   setters сохранены в байткоде, но численно в этой серии не моделировались.
3. 12 точных protobuf-дескрипторов Kanzi: 36 сообщений, 109 полей,
   30 перечислений, 172 значения enum, включая вложенные типы.
   Все 12 бинарных дескрипторов побайтно совпали со строками исходных DEX.
   Зависимости успешно разрешены стандартным protobuf DescriptorPool.
   KANZI_PROTOCOL_RU.txt — читаемый реестр; protobuf_descriptors — JSON/bin;
   kanzi-descriptor-set.pb — объединённый FileDescriptorSet.
4. kx11_ambient_palette.json — все 72 позиции RGB-палитры KX11.
   sdk_integer_constant_dictionary.json — именованные целочисленные константы
   adaptapi с исходным файлом и строкой. Наличие константы не доказывает поддержку.
5. parameter_handlers.bytecode.txt и widget_paths.bytecode.txt — байткод
   обработчиков и конкретных экранов для проверки декомпиляции.
   verification.json: 12 проверок дескрипторов и 13 выбранных преобразований
   аргументов SDK. Это выборочная проверка, не верификация всех сценариев.

АТМОСФЕРНАЯ ПОДСВЕТКА: НЕЛЬЗЯ СМЕШИВАТЬ ДВА ИНТЕРФЕЙСА
Общий ConvertHelper.convert(type=25):
  ID62: диапазон Process 1..10.
  ID63: 0..DEFAULT_COLOR.length-1; DEFAULT_COLOR содержит 42 цвета.
Но конкретный экран ui/light/KXAmbienceFrag строит свои ColorSeekBar:
  цвет — KX11_COLOR / KX11_COLOR_VALUE, 72 позиции 0..71;
  яркость — 21 позиция 0..20.
Колбэк цвета передаёт RGB-число из KX11_COLOR_VALUE, а не номер позиции.
Например: позиция 0 -> RGB(0,84,255) -> 21759 (0x0054FF),
позиция 23 -> RGB(255,0,0) -> 16711680 (0xFF0000).
Позиции 23 и 24 одинакового цвета; число позиций не равно числу уникальных цветов.

setAmbientColor сохраняет RGB в mColor. При завершении жеста ColorSeekBar
отправляет маркер -1; при modeStatus==1 запись ID63 откладывается на 500 мс.
AtmosphereLampsProxy.setFunctionIndex(ID63) передаёт RGB через
setFunctionValue(supportId, Integer.MIN_VALUE, RGB).
Яркость сохраняется в mAmbientBrightness и при маркере -1 передаётся ID62
через setCustomizeFunctionValue(supportId, Integer.MIN_VALUE, float).
Анимационное AmbienceEvent отдельно получает position*5, то есть шкалу 0..100.
Числа 1..10, 0..20, 0..100 и RGB относятся к разным путям и не взаимозаменяемы.
Действительный диапазон, принимаемый установленным SDK/оборудованием, здесь
не измерялся. Значение Integer.MIN_VALUE сохранено как аргумент зоны без
предположения о его физическом смысле.

AtmosphereLampsProxy ID102 -> свойство 537526784:
  индекс 0 -> 0;
  индекс 1 -> 537526787 (AMBIENCE_LIGHT_MAINCOLOR_SETCOLOR);
  индекс 2 -> 537526786 (AMBIENCE_LIGHT_MAINCOLOR_DRIVERMODE);
  прочие индексы -> 0.
ID300 -> свойство 705167616:
  индекс 1 -> 705167617;
  индекс 2 -> 705167618;
  индекс 3 -> 705167619;
  остальные -> 705167617.
Кнопки KXAmbienceFrag выбирают ручной цвет ID102=1 либо режим движения ID102=2;
эффекты назначаются ID300, в просмотренных обработчиках используются 1 и 3.
SharedUtils/default: ambience_type сохраняет выбор 1/2, это локальная память
предпочтения, а не самостоятельная аппаратная команда.
ID262 — отдельный переключатель, запись 1/0.
В setAmbientMode есть переход AM_BREATHING -> индекс 3 ID102, тогда как proxy
для индекса 3 записывает 0. Это расхождение двух методов; достижимость этого
пути и реальный дефект интерфейса ещё не установлены.

СВЕТ, ЯРКОСТЬ, РЕЖИМЫ ЭКРАНА
LightingProxy, type2 ID1: задержка выключения фар:
  0/выкл -> 0; 1/30с -> 537134849; 2/60с -> 537134850;
  3/90с -> 537134851; свойство 537134848.
ID65: property 538247424:
  0 -> 538247427 AUTO; 1 -> 538247425 DAY;
  2 -> 538247426 NIGHT; 3 -> 538247428 CUSTOM.
KXDayAndNightFrag использует две radioGroup: первая передаёт i,
вторая i+2. Простой порядок checkList из другого JSON недостаточен для
определения итогового кода. Список интерфейса и код SDK хранятся раздельно.
ID400/401: пользовательские время дня/ночи передаются float через
setCustomFunctionValue. Формат подтверждён в TimeSettingsDialog: строка HH:MM
превращается в float HH.MM заменой двоеточия на точку, затем передаётся extra
"time". Пример: 08:30 -> 8.3, а не 8.5 часа и не Unix-время. Допустимые
пункты определяются ресурсными массивами sys_time_24/sys_time_12.
TimeUtils.translateTimeTo24 в AM-ветке заменяет на ноль только ровно 12.0;
12.30 AM остаётся 12.3. Для такого входа это расходится с обычной конверсией
в 00:30; наличие соответствующего пункта в ресурсном массиве ещё не проверено.

ID57 — яркость основного экрана, зона 1;
ID169 — яркость пассажирского экрана, зона 4.
Оба выбирают property 538247936 днём / 538248192 ночью.
Их пределы читаются getCustomizeFunctionValue:
  MIN=538248704; MAX=538248448.
ID58 — подсветка приборов, отдельные SETTING_FUNC_BRIGHTNESS_BACKLIGHT
и *_MIN/*_MAX. defaultValue=16 в JSON не устанавливает аппаратный максимум.
ConvertHelper для type1/38 ID20 задаёт 1..5; ID222 задаёт -10..10;
ID237/239 читают MIN/MAX/VALUE предупреждения скорости через IADAS.
Не приписываем этим числам км/ч без подтверждения единиц внешнего API.
convertFixedVolume содержит 0..20 для ID47/50/276, 0..25 для ID48,
0..18 для ID49; достижимость этого private-метода отдельно не доказана.

РЕЖИМЫ ДВИЖЕНИЯ
DriveModeProxy и CarFunctionProxy.setCurDrivingMode передают значение напрямую
в property 570491136. Это НЕ индексы 0..5.
В DriveModeFragment массив кандидатов:
  Comfort 570491138; Eco 570491137; Dynamic 570491139;
  Snow 570491145; Offroad 570491155; Adaptive 570491158.
Поддерживаемый набор приходит из getSupportedFunctionValue(570491136).
Перед выбором UI проверяет isPublicActive. Шесть названий в коде не доказывают,
что все шесть доступны на данной комплектации. Расширенные значения SDK
приведены в словаре, а не объявлены поддерживаемыми автомобилем.

KANZI: ПРОТОКОЛ И НАПРАВЛЕНИЯ
KanziManager создаёт MessageWrapper(cmdID,messageBytes), сериализует protobuf
и вызывает ECarxKanziLib.Request -> очередь KanziView -> SendToKanzi.
KanziView загружает библиотеку "kanzi". Её тела нет среди 18 ранее извлечённых
ELF этого update. Мост Java восстановлен; native-разбор KZB/его поведения
этим не заменён. Числа ниже — ID графического протокола, не CAN-команды.

Основные VehicleCmds:
  1 CommonSet; 3000 AnimationTo; 3001 TrunkControl; 3002 SunroofControl;
  3003 DriveModeSet; 3004 HUDSetting; 3005 SeatBelt; 3006 CarLock;
  3007 OutsideRearMirror; 3008 RainWiper; 3009 CarLocate;
  3010 AmbientLight; 3011 WelcomeLight; 3012 DoorLight; 3013 OutsideLight;
  3014 SeatAdjustment; 3015 DriverEasyInout; 3016 AC;
  3017 CarControl; 3018 SteeringWheel; 3019 SteeringDoor; 3020 SteeringHood.
Наличие enum не равно наличию вызова соответствующего метода в приложении.
Полный набор, климатические команды, поля сообщений и перечисления —
KANZI_PROTOCOL_RU.txt (имена сохранены без исправления опечаток).

HUDSetting, пакет cmdID=3004:
  field1 bool isOpen;
  field2 bool isOpenHeightAndBrightness;
  field3 bool isOpenAR;
  field4 bool isOpenHudSnow.
setHudHeightAndBrightness/setHudAR/setHudSnow также задают isOpen=true
в сохраняемом builder. Это состояние визуализации, не доказательство
принудительного включения физического HUD. Остальные поля builder сохраняются
между вызовами. CarSettingActivity получает Rx-события и передаёт их KanziManager.
setColorAmbientMode независимо записывает в анимационный builder DM_COMFORT;
это не означает перевод реальной трансмиссии в Comfort.

Обратный путь: ECarxKanziLib.onRequest/onAck -> KanziManager.recvMessageWrapper.
Этот конкретный диспетчер обрабатывает только 3000, 4001, 4002.
Enum ACK_ANIMATION_TO равен 4000, но ветка animation callback проверяет 3000.
Фиксируем несовпадение; без native-отправителя не утверждаем неисправность.
4001 TrunkControlEvent обновляет cached percent/status; в этом методе нет
непосредственной записи в ICarFunction.
4002 SunroofControlEvent вызывает progress/status listeners, крайние значения
0.0 и 1.0 превращаются в статусы 0 и 4. CarSettingActivity публикует их в RxBus;
WindowFragOld подписывается на эти события. Это не подтверждает отдельную
команду физическому люку на каждом кадре анимации.
ECarxKanziLib.Request возвращает первоначальное -1 после постановки в очередь;
результат SendToKanzi присваивается позже. Без синхронизации такой return
нельзя использовать как надёжное подтверждение завершившейся операции.

ЧТО ОСТАЁТСЯ ОТКРЫТЫМ
Это существенное расширение параметров, но не полный дамп установленной системы.
Не восстановлены отсутствующие implementation adaptapi/HAL, native libkanzi,
текущие Settings DB/оверлеи машины, интерпретация всех KZB-свойств и все
динамические диапазоны. Не все Java-методы после декомпиляции корректно
реконструированы; при расхождениях сохранён исходный байткод.
Дальнейшие конкретные точки: полные массивы выбора времени и AM-конверсия, пути аудио,
кастомные экраны сидений/климата, соответствие KZB-свойств protobuf-полям,
достижимость несовпадающих ветвей ambience и animation ACK.
