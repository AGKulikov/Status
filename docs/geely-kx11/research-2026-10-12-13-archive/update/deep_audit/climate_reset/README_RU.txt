ТЕМПЕРАТУРА
GMC a/s3/*: HVAC_FUNC_TEMP=268828928; значение Float, далее
FunctionManager -> setCustomizeFunctionValue(functionId,zone,float).
Зоны: основная/водитель=1, пассажир=4, задний ряд=16.
Голосовые шаблоны установки содержат {17-32}, но helper a/s3/a.m(D)F
ограничивает результат диапазоном 17.0..30.0. Оба double-порога проверены
по исходным битовым константам DEX. Поэтому 31 и 32 через этот путь дадут 30.
Это предел конкретного обработчика, не установленный аппаратный максимум.
SDK отдельно объявляет TEMP_MIN/MAX/STEP/UNIT; этот helper их не запрашивает.

Команды «больше/меньше температура» в a/s3/c,d,f,h меняют текущее значение
на +/-1.5, затем используют тот же clamp17..30. Задний ряд — зона16,
основная зона —1. Чтение запускается сообщением через100мс, запись планируется
через350мс после чтения. Значение берётся из результата чтения до этой паузы;
ручное изменение за это время потенциально может быть перезаписано старым
значением плюс/минус1.5. Реальную гонку не воспроизводили.
Пассажирская установка в a/s3/g передаёт зону4 через100мс.

ВОССТАНОВЛЕНИЕ ТЕМПЕРАТУРЫ ПАССАЖИРА
GMC a/r2/n:
 save_last_temperature_state_key — включение функции (Global, default0).
 fix_last_temperature_driver / fix_last_temperature_passenger — Float Global.
Watcher сохраняет значения>0 для зон1/4. При старте восстановление планируется,
если включена настройка, пассажирское значение не -1 и отличается от водительского.
Записывается только пассажирская зона4; эта логика не восстанавливает обе зоны
симметрично. При неудачном результате SDK повтор через350мс, верхнего счётчика
попыток в этом обработчике нет. При успехе посылается сообщение остановки1.

Подтверждённая ошибка отмены очереди: ветка what=1 вызывает
 removeCallbacksAndMessages(Integer.valueOf(0));
 removeCallbacksAndMessages(Integer.valueOf(1));
DEX явно содержит Integer.valueOf перед обоими вызовами — это не null.
По контракту Android данный метод выбирает по Message.obj (токен), а не what.
Для удаления по номеру существует removeMessages(int what).
Использованные sendEmptyMessageDelayed не задают obj=этим Integer-токенам.
Следовательно, эти два вызова не удаляют ожидающие пустые сообщения0/1;
уже поставленная повторная попытка может выполниться после stop-сообщения.
Это вывод по конкретному пути, не утверждение о неизбежном конфликте в машине.
Официальный контракт проверен 13.10.2026:
https://developer.android.com/reference/android/os/Handler#removeCallbacksAndMessages(java.lang.Object)

ПИТАНИЕ КЛИМАТА, AUTO И A/C
HVAC_FUNC_POWER=268501248; HVAC_FUNC_AUTO=268501504;
HVAC_FUNC_AC=268501760 — три разные функции.
a/o3/b «выключить климат»: POWER=0 без явной зоны.
a/o3/c «включить климат»: POWER=1 -> Thread.sleep350мс -> AUTO=1.
a/o3/d «выключить кондиционер»: AC=0, не выключение POWER.
a/o3/e «включить кондиционер»: постановка сообщения через100мс,
 затем POWER=1 -> через500мс AC=1.
a/o3/f,g задний ряд: зона128, POWER=0/1 ->350мс -> AUTO=0/1.
Для заднего ряда питание и направление используют128, температура16.
Нельзя переносить один номер зоны между разными функциями.
В некоторых командах возвращается SUCCESS сразу после постановки сообщения
или вызова setter без проверки фактического состояния. Голосовое подтверждение
само по себе не является подтверждением изменения HVAC.

ОБДУВ: РУЧНОЙ УРОВЕНЬ И ИНТЕНСИВНОСТЬ AUTO
GMC a/p3/b сначала читает AUTO_FAN_SETTING=268567040 в зоне8.
Если результат !=255, выбирается AUTO-ветка:
 ввод<=1 ->268567044 AUTO_FAN_SETTING_QUIETER;
 2 ->268567041 SILENT;
 3 ->268567042 NORMAL;
 4 ->268567043 HIGH;
 >=5 ->268567045 HIGHER.
Имена взяты из IHvac XCSettings2; это не шкала простых целых1..5 в API.

Если результат чтения ==255, используется FAN_SPEED=268566784, зона8:
 ввод<1 ->0;
 1..8 ->268566785..268566792;
 9 и больше ->268566794 FAN_SPEED_LEVEL_AUTO.
Последний переход подтверждён вручную по DEX и проверкой packed-switch:
он содержит ключи1..8, значение9 идёт по default и сохраняет AUTO.
При этом SDK объявляет отдельный FAN_SPEED_LEVEL_9=268566793.
Значит голосовая установка9 не эквивалентна аппаратному уровню9.

Команды +/- обдув (a/p3/c,d) устроены иначе:
 ручной путь прибавляет/вычитает1 из текущего enum и ограничивает
 268566785..268566793 — то есть уровни1..9, без выключения0;
 AUTO-путь ограничивает результат диапазоном268567044..268567045.
Эта числовая граница оставляет только QUIETER/HIGHER и не соответствует
пятиступенчатой таблице явной установки. Например NORMAL268567042 при
прибавлении1 оказывается ниже MIN268567044 и превращается в QUIETER.
Границы и арифметика просмотрены в байткоде; реакция SDK не проверялась.
Нельзя считать enum-коды порядковой шкалой без явного списка переходов.

СБРОСЫ XCSettings2: ДВА РАЗНЫХ МАРШРУТА
resetSettingDataDefault (настройки):
 resetStart -> Bluetooth.init -> IO-задача:
 Wi-Fi default -> Bluetooth.resetDefault -> resetVehicle -> resetDisplay ->
 resetAudio -> resetNotification -> callback resetEnd на основном потоке.
resetVehicle вызывает IUserProfile.resetUserProfileDataDefault(0), если
менеджер доступен. Смысл0 и полный набор параметров определяет внешний SDK.

resetSettingFactoryDefault (заводской):
 resetStart -> FunctionHelper.resetDefault по базе схем -> Bluetooth.init -> IO:
 Wi-Fi default -> Bluetooth.resetDefault -> resetVehicle -> resetAudio ->
 broadcast android.intent.action.FACTORY_RESET с package=android -> resetEnd.
Extra REASON=MasterClearConfirm; WIPE_EXTERNAL_STORAGE=false и WIPE_ESIMS=false
берутся из нового пустого Bundle. Фактическая обработка сброса — в системе,
не в этом APK. Ни один из этих путей не запускался при исследовании.
Здесь resetDisplay/resetNotification напрямую не вызываются; их отсутствие
не означает сохранение параметров после системного factory reset.
resetEnd вызывается после отправки broadcast, не после подтверждения
завершившегося стирания/перезагрузки.

WI-FI И BLUETOOTH
Оба пути передают Wi-Fi reset имя Geely, числовой режим2 и встроенный
DEFAULT_PASSWORD из IWifiProxy; при поддержке band — дополнительный аргумент1.
Это встроенные заводские параметры, не текущие сетевые реквизиты машины.
Bluetooth.resetDefault ставит runnable на main thread: имя Geely,
setVisible(true), при занятых устройствах requestRemoveAclConnected,
затем disconnect/removeBond по кешированному списку.
Это асинхронная операция; следующий resetVehicle не ожидает завершения всех
Bluetooth-разрывов. Общий proxy перед этим обнуляет Bluetooth resetListener.

СБРОС АУДИО: НЕСОГЛАСОВАННОСТИ В ТЕКУЩЕМ APK
resetAudio вызывает ПОСЛЕДОВАТЕЛЬНО resetDefaultAudioAdjust и
resetFactoryDefaultAudioAdjust — даже при обычном сбросе настроек.
Первый задаёт NaviVoiceMixMode1, системную громкость stream5=15 и
SharedUtils/default system_volume=15.
Второй затем задаёт NaviVoiceMixMode2 и system_volume=16, но не делает
соответствующую запись16 в stream5. В рамках этой последовательности реальная
системная громкость и сохранённое предпочтение расходятся:15 против16.
Если какой-либо вызов не прошёл или вмешался другой обработчик, результат иной.

Второй метод вызывает CustomSound.setFunctionIndex с ID47,48,50,49,276 и
значениями16,16,16,10,16. ТЕКУЩИЙ setter обслуживает143,145,146,147,275;
старые ID не приводят к записи аудио. Все пять старых ID проверены отдельными
статическими проходами CFG DEX. Переданный type101 не меняет это: вызов
идёт прямо на тот же объект CustomSound, без повторного выбора proxy.
В первом методе ID53/54 также не обслуживаются соответствующими текущими
setFunctionSwitched/setFunctionIndex (ещё3 проверки).
После этого resetFactoryDefaultAudioAdjust вызывает setStreamMute(true),
который передаёт AudioManager.setStreamMute(3,true) для музыки.
Это подтверждённый вызов в пути сброса, но не доказательство, что mute
останется навсегда: другие компоненты могут снять его позже.

ОХВАТ СБРОСА ПО ТИПАМ ВИДЖЕТОВ
FunctionHelper.resetDefault перебирает runtime-базу FunctionScheme.
resetFunctionSchemeDefault:
 viewType3/4/52 -> boolean(defaultValue!=0);
 viewType2/6/7/23/35 -> index(defaultValue);
 viewType5 -> switch(defaultValue>=0) и index при включении;
 прочие типы не записываются этим методом.
В JSON-ресурсах найдено180 вхождений с viewType, из них35 попадают в указанные
ветки. Это НЕ «сброс работает только для35 настроек»: ресурсы содержат
повторения/элементы навигации, runtime-база может отличаться, есть отдельные
resetDisplay/resetAudio/resetVehicle и системный factory reset.
Файл reset_ui_coverage.json фиксирует каждое вхождение, источник, наличие
явного defaultValue и путь данного метода. Отсутствующий defaultValue не
заменён предположением о фактическом значении базы.
