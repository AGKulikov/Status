Правило доказательности
Каждый вывод относится к конкретному источнику/версии: код update.zip; код системного дампа; наблюдение журнала; предположение. Код и успешный результат вызова не равнозначны физическому изменению. Июльские файлы — снимки на дату сбора, а не подтверждение нынешнего состава системы.
Ранее написанное «компонент отсутствует» в отчётах update.zip означает отсутствие в исследованном пакете, а не во всей кастомной системе. Пакет update.zip не полный образ.

Установлено прямой сверкой
A. XCSettings2 НЕ совпадает с update.zip.
В июльском отчёте ecarx.settings: versionName=20240314-main, versionCode=20240314, путь /system/app/XCSettings2/XCSettings2.apk.
Июльский APK: 305412090 байт, SHA256 4fe63822f44d6f6dfb77564d1b0f9b4aec9fb725c6e1a590862efc1c0ac570e5.
APK обновления: 469059708 байт, SHA256 f4d1b3915324fd2146ea089ca30db4366d5de03fe34f34ef7be49ae4911696e4.
Отличаются не только упаковка/ресурсы: AndroidManifest.xml, classes.dex и classes2.dex имеют разные байты и размеры. Нельзя автоматически переносить весь разбор настроек обновления на июльскую установленную версию. Подробности settings_apk_comparison.json.

B. Внешний AdaptAPI найден в дампе.
framework/system_framework/ecarx.adaptapi.jar, SHA256 87a6fcf44f2a3a2dab7575d6e7a50396b980794074fd5fb5843162fbbde62ef0.
Car.create(Context) вызывает CarImpl.create(Context), а не просто возвращает null. CarImpl.create при ненулевом Context вызывает Authority.verifyAuthority, затем конструктор CarImpl. Это не отменяет проверку прав и не доказывает успешное подключение для любого приложения.
CarImpl создаёт ECarXCarProxy; getSensorManager лениво создаёт Sensor и при установленном соединении передаёт ему CarSignalManager. Таким образом найден конкретный системный слой, которого не хватало для чтения заглушек внутри APK.

C. Цепочка допуска голосовых команд уточнена по системному DEX.
GMC update -> ISensor.getSensorEvent(2097408) -> июльский Sensor.getSensorEvent -> сигнал 30758 -> CarSignalManager.getVehModMngtGlbSafe1UsgModSts -> getSensorEventFromSigVlu.
Таблица преобразования значения сигнала 30758 в этом JAR:
  raw 0  -> 2097410 IGNITION_STATE_LOCK
  raw 1  -> 2097411 IGNITION_STATE_OFF
  raw 2  -> 2097413 IGNITION_STATE_ON
  raw 11 -> 2097414 IGNITION_STATE_START
  raw 13 -> 2097415 IGNITION_STATE_DRIVING
  прочие значения внутри преобразователя -> 2097409 IGNITION_STATE_UNDEFINED.
До преобразования getSensorEvent проверяет значение -1; при недоступном значении/исключении может вернуть -1. Его нельзя подменять UNDEFINED.
Доказательство: sparse-switch key 2097408 -> 0x390; конвертер key 30758 -> 0x20e; явные ветви raw11/raw13 и packed-switch raw0..2. Полные переходы: july_AdaptAPI_switches.json; байткод: july_AdaptAPI.bytecode.txt.
Наименование raw13 UsgModDrvg есть в строке системного логирования. Это режим использования, а не измеренная скорость. Значение ACC есть в интерфейсном enum, но в этой ветке конвертера его нет. Это пример, почему одного SDK-справочника недостаточно.
Комбинированная цепочка применима, только если GMC из обновления работает с этой реализацией AdaptAPI. Совпадение установленной версии GMC и текущей системы пока не доказано.

D. SUCCEED не равно подтверждённому состоянию HUD.
hudlab-runtime.txt из дампа: в 01:03:28 и 01:03:39 ProfileTransfer HUD mode=2 AR возвращает CB33278=SUCCEED, а PA33937 одновременно содержит availability=invalid, dataValue=AR.
В том же журнале многочисленные PEN=-1, а также отдельные ручные передачи PEN=15. Поэтому прежнее упоминание «активный профиль 13» из истории работы нельзя принимать за постоянный профиль этого лога/всех сессий. Здесь автоматическое получение активного PEN не подтверждено.
Эти строки подтверждают результаты инструмента в той сессии. Они не подтверждают включение AR и не дают оснований повторять записи в автомобиль.
