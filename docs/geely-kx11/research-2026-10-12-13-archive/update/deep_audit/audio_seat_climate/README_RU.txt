АУДИО, СИДЕНЬЯ И АВТОПОДОГРЕВ — 13.10.2026

Продолжение разбора update. Исходные APK/DEX не выполнялись. Сохранены байткод
277 методов XCSettings2 и 113 методов GMCSoft выбранных подсистем, включая
внутренние классы. Проверены все 32 комбинации трёх bool-параметров четырёх
регулировок сидений и пять маршрутов громкости. Это не динамические испытания
и не доказательство поддержки функций конкретным автомобилем.

1. ГРОМКОСТЬ: ЛОГИЧЕСКИЙ ТИП НЕ РАВЕН GROUP ID
CustomSound type5 -> CarSoundManager -> StreamVolumeProxy/Policy ->
CarAudioManager.getVolumeGroupIdForUsage -> setGroupVolume(groupId,value,4).

UI ID | логический тип | строка Policy
143   | 2              | NAVIGATION_GUIDANCE
145   | 3              | ASSISTANT
146   | 5              | MEDIA
147   | 6              | VOICE_COMMUNICATION
275   | 11             | TTS

Поэтому передать, например, groupId=5, основываясь только на CustomSound,
неправильно: 5 здесь MEDIA, окончательная группа вычисляется внешней Policy.
Минимум/максимум идут из getGroupMinVolume/getGroupMaxVolume. Значения 0 и 39
в catch — fallback при CarNotConnectedException, не подтверждённые пределы.
При groupId==-1 setAudioVolume вообще не делает запись.

CarSoundManager.onGroupVolumeChanged удаляет ожидающее сообщение своей группы
и ставит новое на 2500 мс. По истечении задержки обновляет UI свежим уровнем.
Повторные уведомления откладывают обновление. setGroupVolume непосредственно
такой задержки не содержит. Это НЕ установленная причина задержек кнопок Natro
или старта плеера — другая подсистема и другой участок исполнения.

CarSoundManager.handleMinAndMaxVolume прекращает ВЕСЬ цикл через return,
если у очередной настройки нет записи/process или max уже больше нуля.
Следующие группы тогда не обрабатываются этим вызовом. loadAllSoundType
повторно не заполняет непустой mVolumeArray. Возможное устаревание диапазонов
при реконнекте требует runtime-проверки; по коду нельзя объявить его причиной
пользовательской неисправности.

2. СИСТЕМНЫЕ ЗВУКИ И ПРЕОБРАЗОВАНИЯ
ID144 использует Android AudioManager, stream=5, независимо от CarAudio-групп.
setFunctionIndex: индекс0 -> громкость25; 1->15; 2->10; прочие->0.
Пишется также Config.SHARED_SYSTEM_VOLUME через SharedUtils.
SoundManager.setStreamVolume(...,true) передаёт flags=4, false -> flags=8.

CustomSound.setFunctionSwitched(ID144,false) сохраняет текущую громкость и
пишет 0. В true-ветке он читает ТЕКУЩУЮ громкость stream5 и пишет её обратно;
сохранённый SharedUtils уровень здесь не читается. Поэтому сама эта ветка
не восстанавливает предыдущую громкость после нуля. Другие обработчики могли
бы её изменить — вывод ограничен данным методом.

ID43: индексы 0/1/прочие -> enhancement 4/1/5.
ID55 и ID165: индекс0 -> NaviVoiceMixMode1, прочие ->2.
ID149: 0/1/2 -> effect 4/1/2, прочие->0.
ID161: 0/1 -> effect1/2, прочие->0.
ID164: индекс0/1/прочие -> speed compensation99/100/101;
       отдельный bool-переключатель включает compensation.
Названия смыслов enhancement/mix должны браться из соответствующего API,
цифры сами по себе не обозначают процент громкости.

CustomSound.setFunctionIndex сначала сравнивает mFunctionId/mValue, затем
обновляет ОБА поля ДО выполнения записи. Та же пара подавляется на следующем
вызове независимо от успешности предыдущего; обратное подтверждение не
участвует. При исключении, отключённом сервисе или groupId=-1 повтор такой же
настройки может быть пропущен. Другой ID/значение обходит этот локальный кеш.
Это статически установленное поведение, а не доказательство наблюдаемого сбоя.

AudioProxy.setNaviVoiceMixMode при исключении вызывает reConnect, но саму
операцию после connect в этом методе не повторяет. CompensationProxy получает
compensation в конструкторе только если AudioProxy.isInit(). В проверенном
классе нет позднего обработчика переприсваивания; некоторые setters проверяют
null, некоторые обращаются напрямую. AudioProxy.init(null) попадает в ветку
setIsInit(true): isInit не гарантирует наличие рабочего объекта audio.
Реальное Audio.create в установленной системе остаётся внешней зависимостью.

3. ЭКВАЛАЙЗЕР И БАЛАНС
EqualizerProxy.getNumberOfBands возвращает фиксированное 3.
Preset читается/выбирается через IEqualizer, а диапазон и уровень полос — через
IHarmanEqualizer. getBandLevelRange приходит из API; ни dB, ни масштаб уровня
по этому proxy не доказаны. При null equalizer setter молча пропускает запись,
getter уровня возвращает 0; ноль не всегда означает подтверждённую настройку.
BalanceProxy.setAudioBalance(float,float) сужает аргументы до short и вызывает
setFaderLevel/setBalanceLevel. Пределы читаются из API-массивов [min,max].
Ресурсная геометрия поля баланса не определяет физические единицы усилителя.

4. СИДЕНЬЯ: КНОПКА, ЗОНА, НАЧАЛО И ОСТАНОВКА
KXAdjustSeatFrag.onTouch обрабатывает action0(DOWN) и action1(UP).
handleClickEvent вызывает CarFunctionProxy; отдельно onSeatClick создаёт
SeatAdjustEvent для Kanzi. Параметр направления анимации иногда противоположен
параметру аппаратного метода. Нельзя копировать boolean из анимации в SDK.

Ось                  | function ID | positive | negative | release
Продольная           | 755106048   |755106049 |755106050 |0
Высота               | 755106304   |755106305 |755106306 |0
Спинка               | 755171840   |755171841 |755171842 |0
Наклон подушки        | 755171584   |755171585 |755171586 |0

Методы вызывают setFunctionValue(function,getSeatIndex(driver),value).
При левом руле driver=true -> зона1, passenger ->4; при правом — наоборот.
Значение down=false всегда выбирает 0, независимо от positive.
Все 32 комбинации driver/positive/down проверены по DEX. Вычисление зоны
сохранено отдельным helper; реальная сторона руля не измерялась.

В onTouch нет отдельной ветки ACTION_CANCEL(3). В собственных onPause и
onDestroyView этого фрагмента найдены удаление VR callback и watcher, но не
вызов остановки движения. Это потенциально неполный путь отпускания жеста.
Нельзя заключать, что кресло реально продолжит движение: неизвестны таймауты
ECU, реализация SDK, обработка родительского view и другие остановочные пути.
Для переноса этой схемы в Natro потребуется отдельная корректная обработка
отмены жеста и потери экрана, а не механическое копирование штатного кода.

Названия функций сверены со словарём XCSettings2 adaptapi.IHvac; это совпадение
констант двух приложений, не подтверждение совместимости всех версий SDK.

GMC hardcode1/4 для водителя/пассажира не повторяет динамическую перестановку
getSeatIndex в XCSettings2. Это различие реализаций, не автоматически ошибка
для конкретной леворульной машины.
Для форсунок FRONT_WASHING_AUTO_HEAT найдены enum, ключи и запись из UI,
но отдельный исполнитель по ссылкам на этот enum в просмотренном Java не
обнаружен. Наличие переключателя не доказывает действующую автоматику форсунок.

Функции обогрева/вентиляции сидений передают выбранный уровень из Settings.Global.
Таймеры отключения лежат в миллисекундах, NONE=-1.
Общий набор сидений/вентиляции/руля: не выключать, 1,2,5,10,15,30,45,60 минут.
Стёкла/форсунки: не выключать, 3,6,9,12,15,30 минут.
Активация и длительность — разные ключи, перечень сохранён на предыдущих этапах.

Стартовая логика сравнивает System.currentTimeMillis()-engine_working_check_last_time
с on_stop_engine_last_time_option; недостаточного интервала или отключённой
настройки достаточно, чтобы стартовая ветка завершилась без включения.
После команды код перечитывает состояние. Для сидений, если оно достигло
целевого уровня, стартует отсчёт времени; при ручном изменении уровня таймер
отключения прекращается, поскольку current!=configured.
Проверка в обычных обработчиках идёт с шагом250мс, переходы —100мс.
Повторы при null имеют отдельные лимиты (5/10 в разных обработчиках).
Не следует распространять эти лимиты на все записи: ветка повторной установки
при ненулевом, но ещё неподходящем состоянии может продолжать отправку каждые
250мс, пока не сменится состояние или не придёт событие остановки.

Стёкла имеют repeat mode:
 back_win_auto_heat_in_repeat_mode_key / front_win_auto_heat_in_repeat_mode_key.
Пока длительность не истекла, каждые5с проверяется состояние и при выключенном
обогреве посылается включение1. После истечения времени выбирается обработчик
отключения0. Поэтому повторное включение может быть намеренной автоматикой.
Существуют broadcast-пути отмены, детали в сохранённом GMCSoft.bytecode.txt.

6. ДОПОЛНИТЕЛЬНО: ЛЮК И ШТОРКА
CarFunctionProxy.openCloseSunBlindSkylight*: UI ID121 -> зона4, прочие ->8.
Короткий путь использует setCustomizeFunctionValue(float), другой —
setFunctionValue(int); один и тот же числовой аргумент не доказывает одинаковую
семантику команд.
slideControlSunBlindSkylight: вход<=9 ->0; иначе выбирается ближайшее значение
из getSupportedFunctionValue(553845504), затем float-setter этой функции.
Это не прямое линейное преобразование любого числа0..100 в положение.
При null списка используется {0}. При пустом массиве getClosestKey не имеет
защиты перед доступом к первому элементу; реально ли API возвращает пустой
массив, неизвестно.
