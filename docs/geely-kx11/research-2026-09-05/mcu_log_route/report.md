# PA_McuLog_Panic: установленный путь журнала MCU в Android

Дата проверки: 2026-09-05. Анализ выполнен исключительно по сохранённым файлам; автомобиль не подключался, код прошивки не исполнялся, сообщения блокам не отправлялись.

**Установлен конкретный входящий маршрут:** IPCP `service 0x0099 / method 0x00C8` → преобразователь PA в `vhal_v1_0_net_impl-lib.so` → VHAL `0x217082F3`, `BYTES`, `READ`, `ON_CHANGE` → SDK `33523 / 0x82F3` → `ECarXCarLogService` → тег Android `ECarXCAR.McuLog_Panic`.

Это журнал, пересланный через автомобильный интерфейс в Android. Наличие строки `[MCU_Version]20.24.10.23024.41141` связывает текст с сообщаемой версией программного обеспечения источника, но **не устанавливает модель процессора, аппаратную плату, полный набор ECU, название исходного образа или его тождество найденному reference-board ELF**.

## Доказательства маршрута

| Участок | Проверенное основание |
|---|---|
| Штатный Java-потребитель | `ECarXCarLogService.initFilter()` добавляет ID `33523`; `ensureTAGById()` сопоставляет ему `ECarXCAR.McuLog_Panic`. `printOutEventLog()` разбирает `PAByteType`, создаёт `PATypes.PA_McuLog_Panic` и печатает полученный текст. |
| Различие имён | Метод прямо заменяет первое `PA_McuLog_Panic` на `PA_McuLog`. Поэтому обёртка `PA_McuLog{...}` в журнале и имя свойства `PA_McuLog_Panic` обозначают этот же путь. |
| Публичный SDK | `ECarXCarMculogpanicManager.getPA_McuLog_Panic()` вызывает `getBytesProperty(33523, 1)` и декодирует `PAByteType`. Это чтение; через него нельзя послать команду ECU. |
| Java → VHAL | В `sdk_to_hal.json`, `read_map`, индекс пары `2144`: `33523 → 561021683 (0x217082F3)`. Таблица уже извлечена из штатного `PropertyIdTransformation`; в этом исследовании соответствие повторно сверено. |
| Native-конфигурация | Конфигурация № `3111`, строка `PA_McuLog_Panic`, `BYTES`, `GLOBAL`, `READ`, `ON_CHANGE`. Адрес записи конфигурации `0x1F6BC0`; строка в ELF `0x1502D2`. |
| Native-диспетчер | `UtilsPAIPCP2VehicleValue::convertPAIpcp2VehicleValues`, начало `0x125B60`. Первый входной `uint16` выбирает таблицу `0x24F370`. Для service `0x99`: индекс `0x99−0x6E=43`, запись по `0x24F41C`, цель `0x12605C`. |
| Проверка метода | В `0x12605C–0x126064` второй `uint16` сравнивается с `0xC8`; иной метод уходит в общий выход. |
| Привязка свойства | По `0x129384–0x129398` загружается литерал из `0x244A00`; его верхние 32 бита по `0x244A04` равны `0x217082F3` и записываются в `VehiclePropValue.prop`. |
| Доставка входа | `EcarxIpcpComm.received_cb()` копирует service, method, payload и адрес/порт peer в очередь. `rxThread()` передаёт service `0x99` в PA-преобразователь, затем переносит полученные `VehiclePropValue` в очередь чтения. |

У обоих независимо сохранённых экземпляров `vhal_v1_0_net_impl-lib.so` — из системного дампа 27 июля и HU-Route 10 августа — SHA-256 одинаков: `b6feed82f777bfa8773c03b78c1f17038e122f492ef85126c095354a29c16756`.

## Раскладка входящего payload

Штатный ожидаемый размер — `0x588 = 1416` байт. Полный UDP payload с заголовком IPCP из 16 байт — `1432` байта.

| Смещение от payload | Размер | Как используется |
|---|---:|---|
| `0x000` | 4 | `availability`, big-endian uint32 → поле Protobuf `1`. |
| `0x004` | 4 | В 45 пакетах `BE32=1400`; предположительно ёмкость текстового поля, не фактическая длина. Данный конвертер поле не читает. |
| `0x008` | до 1400 | Текст с завершающим NUL до области `0x580`; передаётся как Protobuf bytes, поле `2`, далее отображается строкой. |
| `0x580` | 4 | `format`, big-endian uint32 → поле Protobuf `4`. |
| `0x584` | 4 | `status`, big-endian uint32 → поле Protobuf `3`. |

Порядок `format/status` установлен по инструкциям конвертера и сериализатору `PAByteType` (`0x1ACAF8`), а не по порядку Java-полей. В памяти native Protobuf `availability` находится по `+0x28`, `status` по `+0x2C`, `format` по `+0x30`.

При длине, отличной от 1416, штатный конвертер **не обязательно отвергает сообщение**: он логирует несовпадение, копирует `min(length, 1416)` в статический буфер и продолжает преобразование. Поэтому короткий пакет нельзя интерпретировать как свежую полную запись. Приложенный автономный анализатор намеренно декодирует поля только при точной длине 1416.

## Peer и пакетные доказательства

**Независимо повторно прочитан исходный PCAP** `KX11-VP-Action-Evidence-20260815-190324_83890.zip`, `capture/vp-channel.pcap`. В нём найдено 45 входящих `0099/00c8` с полным UDP payload 1432 байта и 45 пустых обратных пакетов этого же service/method по 16 байт.

- Вход: `198.18.34.1:50500 → 198.18.34.15:50335`.
- Интервал наблюдения: `2026-08-15 16:03:50.666451–16:08:16.445467 UTC`.
- Все 45 payload ровно по 1416 байт, `availability=1`, `status=0`, `format=0`.
- Все тексты завершаются NUL; фактическая длина до NUL — 133–861 байт. Декодированы, в частности, сообщения PWR, DIAG и VFC.
- Поле по `+4` во всех 45 пакетах равно `0x00000578 = 1400`. Это согласуется с ёмкостью текстовой области, но **не является фактической длиной текста** в этих пакетах. Семантика «ёмкость» остаётся выводом, поскольку данный конвертер это поле не читает.
- В этом PCAP строки `[MCU_Version]` нет. Значение версии отдельно доказано двумя исходными Android-журналами от 10 августа.

У входящих и пустых обратных пакетов байт `message_type` равен `1`. Поэтому в этом отчёте обратные пакеты называются пустыми обратными пакетами; их протокольная роль не устанавливается только по общеизвестной семантике SOME/IP.

Подробности с номерами пакетов, хешами payload и метаданными: `pcap_mcu_summary.json`. Полные тексты всех 45 сообщений оставлены в рабочей, непубликуемой части анализа.

Дополнительно сохранённый `cruise/pcap_reanalysis.json` предыдущего исследования содержит 64 входящих пакета `0099/00c8 len=1432` в 13 PCAP. 45 из них относятся к только что повторно проверенному файлу; оставшиеся 19 здесь повторно не декодировались. Это не 64 дополнительных пакета.

В дополнительно прочитанном `KX11-Cruise-Trace-20260810-070156.zip`, `pcap/qnx-management-probe/someip.pcap`, целевых пакетов нет. Отсутствие в этой короткой трассе не опровергает наличие канала.

`198.18.34.1` здесь — доказанный транспортный peer Android. Называть его QNX-хостом или физическим MCU без дополнительной связи нельзя: отдельно доказанный qconn-хост имеет адрес `198.18.34.2`. Преобразователь маршрутизирует данные по service/method; сам по себе он не удостоверяет первоначального производителя текста за peer.

## Что означает версия и название Panic

В двух Bus-Capture архивах обнаружены `654` и `653` строки тега `ECarXCAR.McuLog_Panic`; это количество **строк Android-журнала, не число пакетов или событий**. Среди них одинаковая версия, отладочные записи PWR/IPC/DIAG и другие сообщения. Один `PA_McuLog` содержит несколько строк.

`Panic` — имя транспортного свойства и Android-тега. Это не доказательство фактической аварии MCU при каждой строке: через него передаются и обычные сообщения с уровнем `DBG`.

Внутренние временные отметки MCU в тексте нужно отделять от времени получения Android. В одном блоке встречаются начальные `00-00`/`01-01` отметки и последующие реальные даты; повторная выдача накопленного журнала не означает, что все события произошли в момент Android logcat.

## Жизненный цикл штатного сборщика

Конструктор `ECarXCarLogService` создаёт поток `LogService_process`, каталог `/data/McuLog` и задаёт свойство SDK `33285`, area `1`, value `1`. Это `CB_LogServiceStatusAP`, VHAL `0x21408205`; смысл в этом контексте — сообщение о запуске Android-службы журналирования. Отправка обнаружена статически, здесь не выполнялась. Полный транспорт и семантика остальных значений этого CB отдельно не исследованы.

`persist.service.logcat.enable == 1` включает запись полученного текста в файлы. В `printOutEventLog()` вызов `Log.d` стоит до этой проверки: выключатель записи файла не является доказанным выключателем самого входящего канала или Android logcat. Код предусматривает ротацию при 10 MiB и массив из пяти файлов.

## Следующие вопросы после этого результата

1. Связать версию `20.24.10.23024.41141` с конкретным файлом образа по собственному заголовку/метаданным/строке версии и дальнейшему сравнению кода. Одного совпадения строки недостаточно для аппаратной идентичности.
2. Установить процесс и физический домен, владеющий `.1:50500`, и источник журнала за ним. Сохранённые сетевые признаки QNX `.2` не переносятся автоматически на `.1`.
3. Разобрать отдельные журнальные подсистемы PWR/IPC/DIAG по временным шкалам и переходам состояний; не считать сокращение `CC` автоматически круиз-контролем.
4. Установить условия накопления, повторной передачи и потери журнала, значение поля по `+4`, основания изменения availability/status/format.
5. Полностью проследить `CB_LogServiceStatusAP` и регистрацию `ECarXCarLogService`, если потребуется объяснить начало/остановку канала. Это исследование источника, не разрешение менять режим MCU.

Приложения: `evidence.json` — проверяемые адреса, идентификаторы и исходники; `decode_mcu_pcap.py` — локальный анализатор сохранённых PCAP. Полные сторонние декомпиляты и бинарники в публикуемую часть отчёта не входят.
