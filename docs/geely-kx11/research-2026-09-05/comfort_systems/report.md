# Дополнительный разбор кузова и комфорта Geely KX11

Дата: 5 сентября 2026 года. Это расширение технической базы, а не заявление, что все перечисленные устройства установлены в автомобиле. Команды на автомобиле не выполнялись. Полные чужие декомпиляты в этот результат не включены.

Разобран оригинальный `framework/system_framework/ecarx.adaptapi.jar` из архива `ecarx-hud-system-20260727-010640.zip`. SHA-256 библиотеки: `87a6fcf44f2a3a2dab7575d6e7a50396b980794074fd5fb5843162fbbde62ef0`; SHA-256 архива: `9bc62950e55910fc6eb59c99bf80439f7e7ac41f853b4c6c486977e14d062edd`.

К исходным Bcm/Seat/Lamp/Vehicle добавлен прямой разбор реализаций Hvac, Fragrance, AmbienceLight, CarKey, UserProfile, Wpc и SceneMode. `new_function_routes.json` содержит **80 регистраций** из пяти дополнительных функциональных классов: Hvac 50, Fragrance 7, AmbienceLight 13, Wpc 2, SceneMode 8. У 65 найден setter, у 73 — getter. Это статическая регистрация: цифры не означают 65 физически работающих органов управления на KX11. `systems.json` содержит 25 предметных областей с доказательствами, неизвестным, недостающим материалом и следующим офлайн-шагом.

## Новые результаты, влияющие на управление

### Температурный ползунок клиента не совпадает с системным контрактом

В `Hvac.checkTemper`, `convertTemper2Index` и `lambda$buildFunctions$16/17/18` пределы задаются в зависимости от PA 33460:

| Единицы | Минимум | Максимум | Шаг | Кодирование индекса |
|---|---:|---:|---:|---|
| °C | 15,5 | 28,5 | 0,5 | `int((T−15,5)/0,5+1)` |
| °F | 59 | 85 | 1 | `int(T−59+1)` |

Здесь проверены float-инструкции DEX: DAD выводит их битовые значения как большие целые, которые нельзя читать буквально. Диапазон Natro 16–30 °C из прежнего разбора не совпадает с пределами этого SDK. Запросы 29–30 могут отвергаться валидатором ещё до отправки команды. Требуется проверить фактически загруженный SDK, штатное отображение LO/HI и получение min/max/step самим клиентом. Это пока не измерение физических пределов климатической установки.

### В интерфейсе ключей есть настоящие заглушки

`CarKey.createDigitalKey`, удаление одного/всех цифровых ключей и регистрация цифровых callback возвращают `false` без действий. `getDigitalKeys()` создаёт пустой массив; `cancelDiscovery()` ничего не делает. Наличие этих методов не означает реализованные цифровые ключи.

В то же время `startDiscovery`, `readRealKey` и `unbindCarKey` вызывают `CB_PSET_ConnectKey`, property 33254, с кодами 0, 1 и 17. `readRealKey` — отправка запроса, а не пассивное чтение. `unbindCarKey(int)` **игнорирует аргумент** и всегда пишет 17. Его нельзя использовать как доказанный способ удалить определённый ключ по ID. Следующий шаг — разобрать PA callback 33853 и штатный consumer привязки; не запускать операции привязки/отвязки для разведки.

### Создание профиля может произойти при возвращённом −1

`UserProfile.addUserProfile()` и `addUserProfileCopyFrom()` после проверки допуска отправляют `CB_PSET_NewProfile` (33249), но **всегда возвращают −1**. Создание отслеживается асинхронно через PA, а не возвращаемым ID. Повторять вызов из-за −1 нельзя без проверки результата.

Допуск операций берётся из `PA_PSET_PChangeAllowed` 33855: `data == 1`. `getUserProfileData` и `applyUserProfileData` обслуживают только текущий профиль. Последний возвращает `true` после вызова `void`-команды `CB_PSET_ProfileCloudData`, не дожидаясь асинхронного подтверждения результата. `switchUserProfile(from,to)` игнорирует `from`; если `to` уже текущий, возвращает успех без переключения. Эти различия требуют отдельной модели асинхронного результата для профилей. Внутреннее содержимое профиля, атомарность восстановления сиденья/зеркал и облачная синхронизация ещё не разобраны полностью.

### Центральный и детский замки — разные возможности

`BCM_FUNC_DOOR_LOCK` 0x21020200 читает signal 30611 с фиксированным `active`, но setter отсутствует. Зато детские замки 0x21020400 имеют подтверждённые статические CB для зон 16 и 64: command 33243/33244, feedback 33841/33842. Их public 1/0 переводятся в command raw 2/1; обратная связь raw 1/2 — в public 1/0. Это разные кодировки запроса и статуса.

Отдельная функция детских замков для сценария 0x21020700 использует command 33245/33246 и feedback 33843/33844. Её нельзя считать синонимом обычного ручного управления. Установленность электроприводов детской блокировки необходимо проверить по комплектации и PA.

### REQUEST в климате часто означает входящее предложение

| Семейство | REQUEST | CONFIRM | Преобразование public 0 / 1 / 2 в raw |
|---|---|---|---|
| Ионизация / PM2.5 | 0x100c0200: событие без setter | 0x100c0300 → `CB_PM25_HmiPopUpResp`, 32862 | 2 / 1 / 0 |
| Осушение | 0x100d0100: событие без setter | 0x100d0200 → `CB_CL_HumPop`, 32821 | 0 / 1 / 1 |
| Предложение закрыть окна | 0x100f0200: событие без setter | 0x100f0300 → `CB_CL_ClmCloseWinPop`, 32839 | 0 / 1 / 0 |

CONFIRM здесь — ответы без собственного getter. Общая обработка «0 = отмена, 1 = согласие, 2 = закрыть» без проверки каждого штатного диалога будет неверной. Нужно установить смысл каждой кнопки и связь ответа с актуальным предложением. REQUEST не следует превращать в команду запуска.

### Ароматизация: включение сбрасывает интенсивность на среднюю

`Fragrance` для общего on/off 0x100b0100 использует тот же `CB_Fragra_LvlReq` (32869), что отдельный уровень 0x100b0300. При on отправляется raw 2, при off — raw 0. Таким образом, включение не обещает восстановление последнего уровня.

Функция 0x100b0200 объявляет шесть названий ароматов, но зарегистрирована **только со статусом, без getter и setter**. Реальный выбор слота 0x100b0400 переключает A/B/C через соответствующий `TypRatReq(100)`. Чтение type-ID 0x100b0500 использует идентификатор слота как zone. Список ароматов нельзя выдавать за содержимое установленных картриджей. Допуск регулировки уровня дополнительно становится `notactive`, когда PA 33406 содержит 3.

### Массаж: OFF и LEVEL1 совпадают только в mapper интенсивности

Массаж разделён на три функции: intensity 0x10050700, switch 0x10050a00 и program 0x10050b00. В mapper интенсивности **public 0 и LEVEL1 оба становятся raw 0**. Поэтому «выключить массаж» нельзя выводить из имени `SEAT_MASSAGE_OFF`: нужно использовать и подтвердить отдельный switch.

Реализованы программы 1–8 → raw 0–7. Первая исключается при недоступности PA 33621/33622 (hot-stone); программы 9/A имеются в декларациях, но не в этом mapper. Это общий SDK, а не подтверждение массажных элементов в сиденьях Monjaro.

### AUTO подогрева руля имеет отдельные статус и переключатель

0x10090200 объявляет AUTO уровни, но является read-only: signal 30472 преобразуется как 0 → off, любое другое значение → LEVEL1. Уровни 2/3 из declared list этот getter не различает. Запись AUTO выполняется через отдельную 0x10090400 → `CB_SWH_AutoReq` 32859 / PA 33383. Состояние ручного подогрева дополнительно учитывает PA 33385: `data == 5` даёт `error`.

### Сценарии салона управляют одним общим селектором

| Сценарий | Public function | Raw выбранного общего режима |
|---|---|---:|
| Мойка | 0x2f010200 | 9 |
| Дети | 0x2f010600 | 2 |
| Пробуждение | 0x2f020200 | 1 |
| Романтический | 0x2f020600 | 4 |
| King | 0x2f020700 | 11 |
| Queen | 0x2f020900 | 14 |
| Короткий отдых | 0x2f020800 | 3 |

Все семь вызывают `CB_SCEMOD_SceneModSeld` (33272), читают PA 33926 и при off отправляют общий raw 0. Это один режим с несколькими представлениями, а не семь независимых флагов. Отложенное выключение старого режима способно затронуть уже выбранный другой режим. «Театр» 0x2f010100 — другой маршрут: zone 4, `CB_SCEMOD_PassSceneModSeld` 33271, PA 33928, raw 6.

Состав физических действий сценариев — свет, климат, сиденья, окна, экраны — ещё нужно восстанавливать. Само имя режима не определяет его реальные эффекты.

### Подсветка KX11 использует собственную палитру и блокируется сценарием King

`AmbienceLight` регистрирует 0x200a0900 с 72 RGB integer entries для KX11 и иной палитрой из 64 entries для EX11. KX11 использует DEFAULT-zone; EX11 имеет отдельное зонирование. Это другой контракт, чем 13 именованных цветов в клиентском каталоге.

PA 33926 == 11 распознаётся как King scene. В этом режиме 24 проверки состояния подсветки переводят `active` в `notactive`: цвет, яркость, напоминания и эффекты могут временно отключаться вследствие сценария.

Есть и несогласованность SDK: `getAmbienceLightModeSupportedValue()` может добавить BREATHE 0x200a0206 по PA 33799. Но `setAmbLiMod` обрабатывает 0, 0x200a0202/03/04/08; для 06 сначала отправляет `CB_AmbLiAll(1)`, затем возвращает FAILED без установки режима. Здесь FAILED не доказывает отсутствие побочного эффекта. Проверено по switch-байткоду; DAD пропускает часть switch-ветвей.

### Беспроводная зарядка: raw 0 не означает OFF

В `Wpc` work mode 0x26010100 имеет отдельную запись OFF/AUTO. Charge state 0x26020100 — только чтение PA 33626. Его raw 0 преобразуется в OVERHEAT, 1 — STANDBY, 2 — CHARGING, 3 — FOD, 4 — OVERVOLTAGE, 5 — OVERPOWER, 6 — ERROR, 7/9 — OFF, 8 — FULL. Неизвестное значение → 255. Нельзя применять общий boolean-контракт к состоянию зарядки.

## Какие пробелы остались и что делать дальше

25 строк матрицы отдельно охватывают двери/замки, детские замки, ключи, профили, багажник, стёкла, крышу, дворники, зеркала, внешний/внутренний свет, подсветку, семь областей климата/сидений, подогрев руля, WPC, сценарии и датчики. Это матрица изучения, а не завершённый перечень деталей автомобиля.

Сначала продолжить офлайн по уже имеющимся APK/PA/schema: точные потребители профилей и ключей; загрузка версии SDK; штатные climate/scene/ambience UI; соответствие конфигурации, availability и реальных данных. Для окон и сидений отдельно установить правильную остановку, для сценариев — состав действий и правила выхода. Лишь после исчерпания сохранённых источников запросить узкие синхронные наблюдения штатных действий. Дублировать общий дамп или пробовать API по имени оснований нет.
