## Почему сборщик написал partial

Мой сборщик 1.0.0 запускал tcpdump через `adb exec-out`. На фактическом KX11 stdout
и stderr оказались объединены: после 24-байтного заголовка PCAP вставлена строка
tcpdump длиной 81 байт, после всех записей — 78 байт статистики. Оба исходных файла
по 15903 байта. Обычный декодер принял текст за заголовок первой записи и получил
ложную огромную длину пакета; поэтому показал один усечённый пакет и ноль trip-сообщений.
Это дефект сборщика, а не ошибка пользователя или отсутствие данных автомобиля.

В каждом файле сохранены исходные диапазоны `[0,24)` и `[105,15825)`. Удалены
только точная строка `tcpdump: listening…` и точная конечная статистика
20 captured / 20 received / 0 dropped. Все 20 записей по 786 байт непрерывны,
каждый Ethernet-кадр имеет 770 байт. Произвольный текст внутри пакетов не удаляется,
поиск похожих сигнатур внутри повреждённого потока не выполняется.

Проверены длины PCAP, возрастающие timestamps, IPv4 checksum каждого пакета,
UDP checksum при его наличии, адреса/порты и сигнатура IPCP006e/00c8. После
восстановления каждый файл имеет 15744 байта и ровно 20 trip-сообщений, без хвоста
и усечений. Собственный строгий скрипт и полный результат:
[recover_screen_capture.py](../../../tools/geely-trip2/recover_screen_capture.py),
[screen-capture-recovery.json](screen-capture-recovery.json).

## Что передаётся фактически

Записанный сборщиком SHA native VHAL совпадает с ранее исследованным
`b6feed82f777bfa8773c03b78c1f17038e122f492ef85126c095354a29c16756`.
Применён прежний декодер: PA33749 — offset 0x30, PA33751 — offset 0x50 payload.
У обоих полей во всех 40 сообщениях availability=1, format=0, status=0.

| Снимок | Raw времени, начало → конец | Время при секундной шкале | Raw пробега | Интервал пакетов, с |
|---|---|---|---:|---:|
| trip2.pcap | 104311 → 104330 | 28:58:31 → 28:58:50 | 3278504 | 19,059728 |
| trip1.pcap | 104348 → 104367 | 28:59:08 → 28:59:27 | 3278504 | 18,932284 |

При переключении штатной страницы PA-время продолжает идти с секундной скоростью,
пробег не меняется. `/1000` даёт 3278,504 км, `/10` — 327850,4 км: ни один из ранее
обсуждавшихся масштабов не воспроизводит 4,9 либо 7439,7 км. Нужный коэффициент
не выводится подбором под одну фотографию. Даже modulo 24 для времени не даёт
штатную строку. Причина расхождения внутри producer остаётся неизвестной: нельзя
объявлять эти поля одометром, конкретной поездкой или устаревшим кэшем по одному имени.

Фильтр сборщика пропускал только одно сообщение 006e/00c8. Этот архив не содержит
другие сервисы, поэтому по нему нельзя найти иной источник штатной строки или
доказать отсутствие её передачи в других сообщениях. Следующее недостающее звено —
реальный consumer/producer штатных четырёх полей DIM в уже переданных образах и
его маршрут; повторный захват той же PA-пары этот пробел не закроет.

## Исправление транспорта

Исходник сборщика 1.0.1 использует `adb shell -T`, сохраняя раздельные потоки и
код выхода. До tcpdump он проверяет точные бинарные байты 01 00 ff 0a, отдельный
stderr и exit 17 через тот же root-путь. При смешивании, преобразовании байтов
или потере кода выхода запись не начинается. Основание выбора режима —
[официальная справка ADB](https://android.googlesource.com/platform/packages/modules/adb/+/refs/heads/main/docs/user/adb.1.md).

Прошли 15 тестов сборщика, включая воспроизведение смешивания stderr и потери exit
code, и четыре теста восстановления: точное сохранение packet bytes, отказ при
вставке внутри пакета, неполном захвате/ненулевых drops и неверном checksum.
Проверка на новых реальных файлах восстановила 40 сообщений. Исправленный транспорт
1.0.1 на KX11 пока не запускался; новый ZIP сборщика пользователю не требуется для
чтения уже переданных файлов. Код Natro с новым trip-источником здесь не выпускается.

```bash
python3 tools/geely-trip2/recover_screen_capture.py /path/to/Natro-Trip-Check-20260913-113103-9f194d.zip --output /tmp/screen-capture-recovery.json
python3 -m unittest tools.tests.test_trip_screen_collector tools.tests.test_trip_capture_recovery -v
```

## Выданный сборщик 1.0.1

По прямому запросу пользователя передан `Natro-Trip-Check-macOS-v1.0.1.zip`:
12933 байта, SHA-256
`8c69f3ed6103c00e0224d0d98946c2268d89df3d5f8a91cf05f67b718c1da9df`.
Четыре файла комплекта побайтно совпадают с опубликованным commit
`bdc290e1bcef6ff617815b7a9fcbf35cc4af9fce`, tree
`b6fb183c2d566df2d5db316ce7a5609107ba5cd8`.
[CI 34748601272](https://github.com/AGKulikov/Status/actions/runs/34748601272)
успешен. Проверены ZIP CRC, SHA всех файлов, executable mode launcher и запуск
`--plan` после распаковки в путь с пробелами. [Машинный протокол](collector-1.0.1-release.json).

Для запуска распаковать ZIP на Mac и открыть `Collect-Trip-Screens.command`.
В комплекте есть инструкция, нужны прежние ADB и Python 3.8+. Версия исправляет
смешивание PCAP и stderr, но использует прежний фильтр данных. Повторная запись
ради восстановления уже прочитанного архива не нужна. Новый рабочий источник
штатной поездки или аппаратная проверка транспорта этим ZIP не заявляются.
