# Bluetooth KX11: проверенные тела профилей и граница native backend

Дата анализа: 05.09.2026. Только офлайн-разбор сохранённых файлов. APK не собиралась и не запускалась; команды автомобилю, переключение Bluetooth, изменение конфигурации, pairing и звонки не выполнялись.

**Установлена реальная связь nFore-конфигурации с Android-профилями:** штатные `A2dpSinkService` и `HeadsetClientService` читают `MaxAvpNum` и `MaxHfpNum`, а затем используют эти значения при допуске новых соединений. В данном сохранённом конфиге оба значения равны 2. Это значительно сильнее прежнего вывода по одному имени настройки, но по-прежнему не доказывает два одновременно работающих физических канала и ничего не устанавливает о четырёх ANCS-сессиях.

Источник — `KX11_Bluetooth_Collect_20260815-134614_76337.tar.gz`, SHA-256 `3039f0adb2b3e50d40a7dde70f0de5e9e0bcc9e391ec3cccc9e3cb04277ac05a`. `nForeBluetooth.properties` в этом архиве — **сохранённая текущая конфигурация**, а не доказанный заводской baseline: рядом имеются именованные резервные копии до прошлых BLE-изменений. Использованы только выбранные строки текущего файла: 14 (`MaxAclNum=4`), 21 (`MaxDeviceNum=2`), 32 (`MaxHfpNum=2`), 38 (`MaxAvpNum=2`), 44 (`MaxPbapNum=2`), 201 (`LeScanEnable=true`). Тела потребителей MaxAclNum/MaxDeviceNum/MaxPbapNum в данном ограниченном разборе не установлены; эти параметры не получают расширенной семантики по названию.

После полной проверки 158 оригиналов / 102 внешних архивов прежнее отсутствие `ts-dm-service.apk` **опровергнуто**: два одинаковых экземпляра найдены в Cruise-архивах 09.08.2026; SHA-256 `b42926770416f0e05778a04aaa69b0b69c5dd9f1572babe88813a253df7aa8c1`, 641997 байт. Пакет `com.ts.dm.service`, версия `4.5.9.0`, versionCode `28`. Дополнение `../dm_service_evidence.json` содержит 13 проверенных серверных фактов с APK/DEX SHA и code_item offsets; `../full_corpus_target_coverage.json` фиксирует полную проверку присутствия и её границы.

Сервер требует `car.permission.CHANGE_DM_STATE` для connect/disconnect, переводит DM capability 5/6 в foundation HFP/A2DP, дедуплицирует pending-запросы и через 10000 мс перечитывает состояние. При connected projection capability 1/2 он отключает HFP другого устройства. В profile callback при tracked projection также есть реальный HFP disconnect; соседняя ветка A2DP только пишет log и возвращается. DeviceManager обрабатывает profile callback через Handler с обновлением модели до рассылки; синтетические состояния и таймеры проходят тот же callback путь. Точные методы и пределы: DM01–09, DM13. Пять отобранных arbitration/timeout строк не встречены в шести slices, поэтому эта политика пока не объясняет конкретный Natro-разрыв (DM11).

Для следующего офлайн-шага подготовлен `collection_targets.json`: **8 отсутствующих файлов/ABI**, включая первоочередные `/system/lib64/libbluetooth_jni.so`, `/system/lib64/libbluetooth.so` и `/system/app/EcarxBluetoothServiceExtension/EcarxBluetoothServiceExtension.apk`. Для уже найденного DM APK нужна только свежая metadata/SHA проверка и перенос при изменившемся SHA. Неизвестные baseline SHA остальных файлов оставлены null. Точное имя пакета extension — `ecarx.bluetooth.service.extension`, подтверждённое package listing; его серверные тела пока отсутствуют.

Статический результат сопоставлен с отдельным runtime-отчётом. Установлены GPS/Natro owners в определённых эпохах, но не причина каждого разрыва, одновременные ANCS-сессии или причины внутреннего teardown Natro. Открыты native backend, extension, installed Natro identity и синхронный power epoch; наличие восстановленной DM-политики не доказывает её исполнение в этих событиях.

Исходные бинарники и рабочий дизассемблерный вывод находятся только в `private/`. Данные pairing, базы приложений, контакты, история звонков, HCI payload и тексты уведомлений не читались и не включены в результат. Natro 2.7.7, NOTIF-009 и его запрет TTL не менялись; аппаратные критерии не закрыты.
