# Навигация и HUD v2

## Решение

Natro хранит настройки и компонует интерфейс. Минимальный патч Яндекс Навигатора 30.3.0
остаётся единственным владельцем активной навигационной сессии и MapKit. Второй маршрут в Natro
не рассчитывается: основной экран и HUD всегда показывают одну и ту же сессию.

## Граница компонентов

- Навигатор публикует версионированный `NavigationSnapshotV2`: положение, курс, манёвр,
  расстояния, ETA, полосы и ограничение скорости. Тяжёлая геометрия маршрута передаётся отдельно
  в `NavigationRouteGeometryV2` только при смене `routeEpoch`, а не в каждом кадре.
- Для HUD Навигатор создаёт отдельный `OffscreenMapWindow` и рисует прямо в `Surface`, который
  предоставляет Natro. Кадры не проходят через `ImageReader`, `Bitmap` или MediaProjection.
- Natro размещает карту и любые текстовые/векторные элементы независимо по всей области HUD.
- Основная карта и HUD-карта получают разные `MapProfile`: камера, zoom, наклон, day/night,
  слои, JSON-стили, маршрут и курсор не связаны между собой.
- Геометрию, фиксацию перемещения/размера, скругление, прозрачность, рамку и тень плавающего окна
  основной карты применяет патч Навигатора к собственному окну. Natro только редактирует и
  передаёт `FloatingWindowProfile`.

## IPC

Используется явный bound service и `Messenger`-контракт версии 2 из
`NavigationBridgeContract`. При подключении обе стороны обмениваются возможностями. Навигатор
проверяет пакет и SHA-256 сертификата клиента. Широковещательные команды без проверки отправителя
для управления картой не используются.

## Миграция

Экспериментальный `NAV_MAP`, `NavigatorMapFrameProvider`, `NavigatorHudBridgeService` и
покадровое RGBA-копирование удалены. Старый элемент карты пропускается при чтении layout schema 4;
остальные пользовательские элементы сохраняются. Новая карта появится как новый surface-элемент
после реализации и проверки bridge в моде 30.3.0.

## Этапы

1. Удалить старый frame-copy путь и зафиксировать контракт/модели конфигурации.
2. Патч 30.3.0: snapshot + capabilities + независимый `OffscreenMapWindow` + main floating API.
3. Natro: surface-элемент HUD, два независимых редактора профиля и редактор плавающего окна.
4. Стендовые тесты на виртуальном display, затем физические тесты KX11: QuickBoot, сворачивание,
   перестроение маршрута, day/night, 30 минут движения и последовательные перезагрузки.

## Основания решения

- Yandex MapKit External Surfaces прямо предупреждает: дополнительный `Surface` дублирует
  существующий `MapWindow` с теми же стилями и камерой, управлять им отдельно нельзя:
  https://yandex.com/maps-api/docs/mapkit/android/static/tutorials/map_surface.html
- `OffscreenMapWindow` создаёт отдельный `MapWindow` без `View` и умеет рисовать на переданный
  `Surface`: https://yandex.com/maps-api/docs/mapkit/com/yandex/mapkit/map/OffscreenMapWindow.html
- `hudnav` подтверждает полезную границу «один state repository — два представления», но строит
  собственный маршрут и пока использует упрощённую логику манёвров:
  https://github.com/ingebyd/hudnav/blob/main/CLAUDE.md
- BYDMate использует virtual display/freeform для проекции приложения. Это рабочий fallback для
  зеркала, но не даёт независимую HUD-карту:
  https://github.com/AndyShaman/BYDMate/blob/main/README.en.md
- ynavi-zee показывает воспроизводимый apktool/smali-процесс патча Яндекс Навигатора для ГУ,
  включая масштабирование и keepalive: https://github.com/maxim-saplin/ynavi-zee

Для следующего этапа нужен точный APK модифицированного Навигатора 30.3.0, установленного на ГУ.
Нельзя надёжно привязать smali-hook, проверить состав MapKit и сохранить совместимую подпись по
другой сборке с тем же номером версии.
