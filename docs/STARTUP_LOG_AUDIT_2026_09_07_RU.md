# Запуск приборки, карты и завершение Natro: разбор журнала 07.09.2026

При ручном запуске приборки текущий код принудительно завершает весь пакет Natro.
В журнале также видны повторное пересоздание HUD при восстановлении и отдельное
отключение Navigator при первом вечернем запуске. Причина последнего отключения
из этого экспорта не устанавливается.

## Причины, подтверждённые кодом

1. **Ручной запуск приборки останавливает всё приложение.**
   `InstrumentDisplayLauncher.launch()` выбирает внешний запуск через Navigator.
   `onExternalLaunchPrepared(true)` исполняет
   `am force-stop --user 0 ru.natro.statuswidget`. Вместе с процессом прекращаются
   работающие в нём сервисы и HUD. Это объясняет исчезновение Natro в 18:13:45.
   При этом слово `accepted` в записи сильнее фактической гарантии:
   `NavigationHudEndpointService.prepareInstrumentPanelLaunch()` возвращает успех
   отправки Binder-сообщения, а не подтверждение запуска Activity на приборке.
   Автоматический путь `launchCold()` эту команду не использует.

2. **Восстановление HUD безусловно пересоздаёт визуальную часть.**
   `HudPresentationService.onStartCommand()` при `HUD_LIFECYCLE_RECONCILE` всегда
   вызывает `dismissPresentation()` и повторное создание. Вызовы поступают как из
   BootReceiver, так и из восстановления WidgetService. Три последовательности
   закрытия/создания на одном дисплее вечером подтверждены журналом. Код задуман
   для потери системных окон после QuickBoot, но этот же сброс применяется к
   повторным запросам восстановления. Видимую длительность пустого кадра журнал
   не измеряет; причинной связи с отключением Navigator в 18:08:50 не доказано.

3. **Запись об окончании bridge не объясняет причину отключения.**
   `NavigationHudEndpointService.disconnectCurrentClient()` пишет одинаковый текст
   при `onUnbind`, уничтожении endpoint, смерти удалённого Binder и замене сессии
   новым HELLO. Поэтому по этой строке нельзя установить Java/native crash
   Navigator, системное завершение процесса либо обычное отключение.

## Адресные изменения, требующие реализации и проверки

1. Переработать ручной DIM handoff так, чтобы запуск приборки сохранял процесс
   Natro и его фоновые сервисы. В коде уже есть сброс только выделенного task
   приборки (`finishStalePanelTask`); пригодность этого пути для ручного запуска
   нужно проверить на KX11 с текущими display/options, без возврата запроса
   перенести окно настроек на другой экран. Простое удаление команды не
   доказывает корректность ECARX-последовательности.
2. Разделить обычную повторную проверку HUD и принудительное восстановление после
   фактической потери системной поверхности/QuickBoot; повторный checkpoint не
   должен заново уничтожать уже восстановленное окно.
3. Убрать синхронную запись launch token и загрузку иконок из главного потока.
   Сохранить долговечность и однократность токена: замена `commit()` на `apply()`
   перед завершением процесса не даёт эквивалентной гарантии.
4. Различать в журнале причины отключения bridge; фиксировать принятие/отклонение
   токена и фактический lifecycle/display Activity. Эти данные нужны для
   диагностики, а не для предположения, что уже подключённая карта означает
   успешное отображение всей приборки.

## Чего не хватает для точной причины отдельного падения

Во всём экспорте нет `FATAL EXCEPTION`, `AndroidRuntime`, секции `crash`,
`OutOfMemory` или системного ANR. Их отсутствие не исключает native crash,
завершение Android либо исключение до инициализации собственного журнала.

Нужен системный logcat без фильтра по одному PID: перед повторением сбоя на
подключённом через ADB компьютере запустить команду и после воспроизведения
остановить её через Ctrl+C:

```sh
adb logcat -b main -b system -b events -b crash -v threadtime > natro-startup-system.txt
```

Захват должен включать Natro, Navigator и системные причины завершения; при
перезапуске приложения PID меняется. Файл не следует автоматически публиковать.
При native crash дополнительно нужны tombstone/bugreport, если logcat не содержит
полного стека. При зависании — ANR traces/bugreport.

Обычный «Экспорт TXT» содержит собственный журнал Natro. Текущий расширенный
`PrivilegedActionCollector` читает и crash buffer, но затем пропускает строки
через автомобильный `RELEVANT_LOG`; сохранение полного AndroidRuntime/libc-стека
в «Сессия TXT/JSON» этим фильтром не гарантируется.
