# После установки Navigator mapfix обе карты по-прежнему отсутствуют

13.09.2026 пользователь сообщил: «карта на худе и на пригорке так и не запускается
после обновления навигатора». Это отрицательный аппаратный результат для выданного
обновления. NAV-018 и GATE-082 остаются открытыми: исправленная сигнатура listener,
успешный CI и проверенная подпись не означают восстановление карт.

Выданный Navigator mapfix имеет SHA-256
`1bb5ba22cd2a60726414779fa9d8ebb37973ee756f4e9f401f9efc5bc63da4a2`;
Natro 2.8.8 — `bcbfd5c0fc044d309ada196cc260d7459f89f9956466005bf98d8e4ca1e1db3b`.
Сообщение пользователя принимается как результат установки. Хеши именно
установленных на магнитоле файлов пока не прочитаны; это часть диагностики,
а не предположение об ошибке пользователя.

## Что дополнительно проверено

В фактическом APK mapfix проверены обязательные декларации MapKit: создание
OffscreenMapWindow, получение MapWindow и Map, регистрация WeakReference listener,
SurfaceFactory.from(android.view.Surface), addSurface/removeSurface и
getRenderObjectCount. Эти объявления доступны с нужными сигнатурами. Собственный
результат без чужого bytecode — [mapfix-startup-api-check.json](mapfix-startup-api-check.json).
Проверка не охватывает все необязательные методы MapKit и не исполняет native-код.

После создания renderer остаются отдельные этапы: присоединение Surface, настройка
карты, callback MapLoadedListener с render objects, ACK текущей session/generation
и три содержательных кадра TextureView. По имеющимся файлам неизвестно, какой из
этих этапов не пройден. Исходники не дают основания назвать alpha=0 установленной
причиной или убрать защиту от белого/пустого буфера. Таймаут не заменяет готовность.

Новый архив `Natro-Trip-Check-20260913-121730-3feae8.zip` содержит только два
узких IPCP-снимка поездок; журнала Android и ошибок запуска MapKit в нём нет.
Повтор того же trip-захвата не локализует отказ карт.

## Сборщик нужной диагностики

Подготовлен отдельный комплект [tools/geely-map-check](../../tools/geely-map-check/README_RU.md),
версия 1.0.0. На Mac запускается `Collect-Maps.command`, когда приложения уже
находятся в состоянии отказа. Он сохраняет выбранные logcat-теги, существующий
журнал Natro при доступном root, версии и SHA установленных APK, службы, Activity,
окна, дисплеи и состояние графики. APK и настройки аккаунтов не скачиваются.

Сбор ограничен общим сроком 90 секунд, таймаутами отдельных чтений и пределами
размера. Неполные результаты и ошибки сохраняются в ZIP. Сборщик не перезапускает
приложения, не очищает логи, не пишет автомобильные команды и не меняет настройки.

Восемь офлайн-тестов прошли, включая полный запуск упакованного launcher из пути
с пробелами через fake ADB, частичные ошибки, отсутствие root, смешивание потоков,
несколько устройств, проверку APK-путей, ограничения и воспроизводимость ZIP.
На KX11 этот map-сборщик ещё не выполнялся. Новый APK по непроверенной гипотезе
не выпускался; следующий шаг — сопоставить фактические ошибки, ACK и состояние
поверхностей из собранного архива.

```bash
python3 -m unittest tools.tests.test_map_check_collector -v
python3 tools/geely-map-check/build_bundle.py /tmp/Natro-Map-Check-macOS-v1.0.0.zip
```

`7d45e79ebfd38d95202ea639be72300e16b4b7c45f16ffc2ca61f1919f28abee`. Все пять файлов запуска
равны опубликованному commit `cfd750d67affd1f6aa5f480512ec370e5560c59a`,
tree `d7b743d36fe0dfb0734968f38f4231eb6e85cae6`. Проверены CRC,

стола даже при частичном сборе. Аппаратный запуск сборщика ещё не получен.
