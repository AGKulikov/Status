# Natro 2.7.2: аудит размещения карточек карты

Дата фиксации: 03.09.2026. Статус: исполняемый код и автоматические контракты готовы;
`GATE-020` и `GATE-026` остаются аппаратными проверками KX11.

## Проверенная штатная база

Проверка выполнена по точному Navigator 30.3.0 с SHA-256
`663018fb66074e001eed7caba8e33bee1bcf78f6798bc84949d253dcb348f27f`.
Декомпилированные ресурсы и код Яндекса в репозиторий не добавляются. Зафиксированы только
доступные во время исполнения контракты:

- табличка полос создаётся `LaneSignBalloonTextureFactory`, а её размер и `imageAnchor`
  зависят от `BalloonAnchor`;
- светофор создаётся `TrafficLightViewImpl(Context, scale)`, принимает `LegPlacement`, а его
  `getSize(leg)` и `getAnchor()` задают разную геометрию для каждой стороны;
- фактический bitmap светофора масштабируется коэффициентом конструктора, поэтому размеры из
  `getSize(leg)` переводятся в физические пиксели до collision-расчёта;
- поддерживаются восемь положений: `LEFT_CENTER`, `RIGHT_CENTER`, `TOP_LEFT`, `TOP_CENTER`,
  `TOP_RIGHT`, `BOTTOM_LEFT`, `BOTTOM_CENTER`, `BOTTOM_RIGHT`.

## Неподвижные и подвижные объекты

| Объект | Положение | Причина |
|---|---|---|
| Курсор автомобиля | центр в текущей координате | источник положения водителя; только резервирует место |
| Камера и вершина сектора | центр в точной координате камеры | перенос камеры с маршрута запрещён `MAP-037` |
| Конечная точка | точная координата конца маршрута | географический объект, не карточка |
| Стрелки манёвров | геометрия маршрутной полилинии | нативные объекты MapKit, не placemark |
| Табличка полос | одно из восьми положений | карточка должна обходить маршрут и неподвижные объекты |
| Светофор/секунды | одно из восьми положений | карточка выносится, но tip ножки остаётся в точке события |

Порядок одного прохода: курсор резервируется при начале layout, затем центрированные камеры,
табличка полос и светофоры. Поэтому низкоприоритетная карточка может сменить сторону, но не может
сдвинуть курсор или камеру.

## Как выбирается сторона

Для события сохраняется точная `PolylinePosition` активного маршрута. После каждого существенного
изменения камеры все нужные точки маршрута переводятся в экранные координаты через текущий
`MapWindow.worldToScreen`; это автоматически учитывает zoom, tilt, азимут и размер конкретного
HUD/приборного viewport.

Для каждой из восьми сторон используется реальный размер и anchor будущей текстуры. Суммарная
оценка включает:

1. выход за безопасную границу viewport;
2. пересечение с курсором, камерой и ранее размещённой карточкой;
3. длину экранного маршрута, которую закроет карточка, включая запас вокруг линии;
4. участок подхода от текущего прогресса до события;
5. участок после события с повышенным весом;
6. дополнительный вес ближайшего экранного изгиба, чтобы короткий поворот не проиграл длинному
   прямому участку;
7. порог смены уже выбранной стороны, исключающий дрожание от однопиксельных изменений.

ID или hash события не выбирает сторону. Предпочтение справа используется только как последний
детерминированный tie-breaker при полностью равных безопасных вариантах.

## Ножка светофора

Штатной плашке передаётся тот же выбранный `LegPlacement`, который участвовал в расчёте. Кроме
того, один и тот же placemark использует `CompositeIcon` из двух named parts:

- `traffic-light-body` — штатный renderer либо региональный fallback;
- `traffic-light-connector` — гарантированная screen-facing vector-path ножка, заново
  растрированная с oversampling для выбранного физического масштаба.

Anchor ножки находится на её остром конце и совпадает с неизменённой географической координатой
placemark. Направление к плашке меняется для всех восьми положений. Части заменяются по имени без
`removeAll`, поэтому обновление секунд не создаёт промежуточный пустой кадр и не отделяет ножку
от плашки.

## Повторная сверка порядка слоёв

Механизм не создаёт нового MapKit sublayer: обе части светофора остаются одним placemark в
существующем `TRAFFIC_LIGHTS`, а ножка имеет только локальный `zIndex` на 0,01 ниже собственной
плашки. Поэтому общий порядок `MapSublayerOrder` не изменён:

- сектор камеры остаётся в `GROUND` ниже маршрута;
- маршрут и нативные стрелки остаются одной полилинией;
- дорожные события и камера находятся ниже курсора;
- курсор ниже светофоров, табличек полос и конечной точки;
- screen-space порядок резервирования камера → полосы → светофоры не меняет порядок их
  отрисовки и используется только для выбора свободной стороны.

Автоматический и ручной feature-type-aware порядок по-прежнему проверяется `MAP-034/GATE-019`.

## Автоматическая проверка и аппаратная граница

Java geometry-harness проверяет прямой маршрут, левый и правый поворот, S-образный участок,
азимуты 0/45/90/180/270 градусов, масштабы 50/75/100%, границы viewport, устойчивость стороны и
использование точных per-leg размеров/anchor. Статические контракты отдельно запрещают возврат
Automotive `NavigationLayer`/`GuidanceCamera`, проверяют порядок слоёв и единую композицию ножки.

Эти проверки не доказывают фактический GPU-кадр на двух дисплеях KX11. До закрытия
`GATE-020/GATE-026` нельзя утверждать, что визуальная приёмка, pan/zoom/tilt и 30-минутная
стабильность уже пройдены.
