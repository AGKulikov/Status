# Восстановление всей приборки без завершения Natro

Поручение пользователя 07.09.2026: перевести ручной запуск без self-force-stop и
разобраться с отсутствием всей приборки при загрузке. Основание —
[разбор исходного журнала](STARTUP_LOG_AUDIT_2026_09_07_RU.md) и уточнение пользователя.

В 2.8.1 `InstrumentPanelActivity.isActive()` означал только существование Activity.
`launchCold()` и ручной `launch()` выходили через requestReload ещё до переключения
DIM/пробуждения и запуска task. Скрытая или пережившая потерю дисплея Activity таким
образом блокировала восстановление страницы. Отдельный дефект — после окончания
ожидания отсутствующего дисплея код всё равно вызывал startActivity.
Первый cluster lease не доказывает, что вся приборка физически отображалась.
Точный момент и физическая причина пользовательского эпизода старым журналом не установлены.

Внесённые изменения:

- Ручной и автоматический запуск используют один `InstrumentPanelLaunchCoordinator`.
  Удалены вызов self-force-stop, shell probe, внешний handoff и ожидание Navigator.
- Boot/QuickBoot/восстановление host повторяют прежние DIM mode3 и wake с паузами
  100/200 мс, включая сохранившуюся Activity. Readback режима записывается отдельно;
  подтверждённый mode3 учитывается и при ответе false на установку неизменённого значения.
- Успехом считается STARTED, attached, visible и первый draw на выбранном display с
  положительными размерами. Принятый startActivity остаётся только началом ожидания окна.
  PAUSED/focus не блокируют готовность: Android 9 допускает видимые STARTED Activity
  при единственной RESUMED Activity на другом дисплее.
  [Документация Android](https://developer.android.com/develop/adaptive-apps/guides/support-multi-window-mode).
- Живое окно на правильном дисплее переиспользуется. Удаление устаревшего task
  проверяет точные package и class приборки; задачи настроек и других приложений
  не входят в этот отбор. QuickBoot и реальное изменение доступности/питания дисплея
  пересоздают только собственное окно приборки, сохраняя процесс и фоновые сервисы.
- Отсутствующий/выключенный дисплей ожидается ограниченно, без запасного запуска на
  центральном экране. Автоматический display listener возобновляет попытку при
  позднем появлении/включении выбранного дисплея; он снимается при отключении функции.
- На одну транзакцию допускаются 10 повторов ожидания дисплея и до 3 попыток запуска;
  ожидание подготовки DIM/записи токена/появления окна имеет отдельные пределы 15 с.
  Повторные запросы объединяются, отменённые и запоздавшие callbacks не запускают Activity.
- Выдача, потребление и отзыв токена используют последовательную рабочую очередь,
  общий lock между экземплярами Store и durable commit вне главного потока. Срок жизни
  15 с, однократность и проверка exported Activity сохраняются.
- Журнал содержит источник запроса, skip/cancel/timeout, результат DIM, lifecycle и
  display/размер/видимость/первый draw. До чтения настройки диагностики сохраняются
  максимум 64 очищенные технические записи в памяти; при выключенном debug они
  удаляются, при включённом записываются с исходным временем.

Локально прошли 21 поведенческий JUnit-тест координатора, включая пропавший дисплей,
позднее восстановление, скрытую/неправильно размещённую Activity, отсутствие первого
кадра, выключение во время записи токена, смену дисплея и ограничение повторов.
Полная компиляция приложения и регрессии выполняются отдельным workflow без APK.
Аппаратные GATE-043/059 остаются открытыми; версия установленной пары остаётся 2.8.1.
Отдельный обрыв Navigator и остальные дефекты из аудита не объявляются устранёнными.

Дополнительные настройки оформления табличек и визуальный выбор цветов по новому
сообщению пользователя ведутся отдельно в этой же работе (CARD-020/MAP-054/NATRO-020).
