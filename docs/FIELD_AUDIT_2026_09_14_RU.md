# Проверка журналов и фотографий после 2.9.3

Актуальный результат KX11 отрицательный: белая вспышка и задержки музыки остаются, ANCS после
обновления не восстановился. Исправления ниже подготовлены для пары 2.9.4; они не заменяют
аппаратную приёмку. Данные автомобиля, MConfig и системные input/Bluetooth службы не изменялись.

| Время Android | Наблюдение |

| 07:06:34.992 | Helper и ANCS найдены полностью; Service Changed доступен |

| 07:06:36.901 | Transient failure CCCD Notification Source |
| 07:06:37.104 | Повторный отказ → WAIT_ANCS без таймера |

Наличие ANCS с временным отказом CCCD ошибочно обрабатывалось как отсутствие сервиса:
восстановление зависело от Service Changed, который не обязан появляться при таком отказе.
Новый WAIT_ANCS_RETRY использует один таймер и тот же GATT owner: 1/3/10/30/60 с, далее не чаще
раза в минуту. READY требует успешных NS и DS; missing-service и authorization gates сохранены.
Если фактически поставленная ATT-операция остаётся без callback более 30 с, ближайший retry
завершает её owner через существующее ограждение teardown; другой descriptor не подставляется
под поздний callback. Service Changed при таком незавершённом ATT также завершает старый owner.
Добавлены точный Android status, результат постановки CCCD, занятый слот и его возраст.

Сам числовой status отказа CCCD старый журнал не содержит. Причина GATT 133 и причина отказа
на стороне Bluetooth/iOS не доказаны. Android APK не обновляют установленный iPhone Helper.

## Музыка: fsync и доступность наблюдения кнопок

В 07:17:14 главный поток Natro стоит в QueuedWork.waitToFinish/ActivityThread.handleServiceArgs;
queued-work-looper выполняет SharedPreferencesImpl.writeToFile → FileDescriptor.sync. Восстановление
07:17:20.521: stalled_for_ms=8682. Потоки пассивного наблюдения в этом снимке свободны.
Это доказанная блокировка Natro, но не измерение времени физической кнопки и не доказательство
заполнения очереди MConfig. Конкретный файл SharedPreferences по стеку определить нельзя.

Для трёх частых кэшей — навигация, позиция/метаданные музыки, телеметрия телефона — введён
RuntimeSnapshotPreferences. Изменение сразу доступно в памяти; единственный фоновый checkpoint
сохраняет последний снимок через commit, без framework apply/QueuedWork. Пока диск занят, новые
значения заменяют ожидаемый снимок, не накапливая старые записи. Интервал 5 с; при аварийном
завершении процесса последние несохранённые данные кэша могут потеряться. Правила свежести,
boot/address attribution сохранены. Настройки, enrollment, ownership, управляющие команды и WAL
на этот механизм не переводятся. Legacy отдельный HUD сохраняет прежнее чтение с диска.

Пассивный receiver в новом журнале 2.9.3 получил **0 broadcast**, хотя видел три MediaSession.
Дополнительно введено чтение только key-полей logcat известных input/media tags при **уже
выданном READ_LOGS**. Оно включается с debug/Action Recorder, работает отдельно от main/Binder,
ограничено по частоте и прекращается при выключении записи. Команды, root и выдача разрешений
не выполняются. Неполный системный текст не превращается в выдуманный KeyEvent/eventTime;
исходный текст, названия треков и произвольные сообщения не сохраняются. Coverage явно сообщает
об отсутствии разрешения или записей прошивки. Временная связь с MediaSession не является
подтверждением звука, исполнения команды или физического происхождения кнопки.

## Камеры: обычный pin и составной знак

Повторно прочитана штатная библиотека Navigator 30.3.0: libmaps-mobile.so, SHA-256
`93e2334589328cbe9d1082925caeb9c2631cde43983aaab112c197fdf4885069`.
PlatformIconsProviderImpl формирует несколько RoadEventContent; Java PlatformImageProviderImpl
передаёт их RoadEventPlatformImage. Это другой путь, чем max-priority ordinary pin style provider.
Проверены соответствующие native ветви SPEED_CONTROL, LANE_CONTROL/ROAD_MARKING_CONTROL,
CROSS_ROAD_CONTROL и NO_STOPPING_CONTROL и Java композиция содержимого. Закрытый код не копируется.

| Вход одного события после фильтра видимости | Новый состав |
|---|---|
| SPEED_CONTROL и известный limit | Только скорость |
| LANE_CONTROL/ROAD_MARKING_CONTROL без SPEED_CONTROL, даже при limit=110 | Только разметка |
| LANE_CONTROL/ROAD_MARKING_CONTROL + SPEED_CONTROL, известный limit | Разметка и скорость |
| Несколько тегов одной и той же таблички | Одна копия этой таблички |
| Самостоятельные соседние event IDs | Отдельные события |

Обычный stock pin выбирается только для диагностики, больше не удаляет половину составного
знака. Положительное road speed value само по себе не создаёт контроль скорости. Малые camera
pins под единой композицией остаются исключёнными. Полнота route events и независимых ДТП
сохранена. Нативные upstream фильтры, настройки и различия исходных событий ещё требуют
проверки на маршруте; три фотографии не доказывают соответствие всех типов.

## Светофор и старт карты

На IMG_8401 у одной live-карточки виден хвостик, у второй нет. В расчёте размещения обнаружено
несоответствие: TrafficLightViewImpl.getSize(leg) не включает тень, а createTexture/getAnchor
используют полную рамку с тенью. Добавлен расчёт union с radius/offset и штатным масштабом.
Тело/хвост по-прежнему одна stock текстура; отдельный указатель не создаётся. Диагностика при
изменении геометрии сообщает ID, stock/compact, сторону, размеры и anchor; countdown не создаёт
ежесекундный повтор такой записи. Переход на fallback теперь виден в журнале. Это исправление
границ размещения, **не доказанная первопричина** пропавшего хвостика на фотографии.

Вспышка: защита 2.9.3 на приборке сработала, но симптом остался. Профиль карты применяется до
addSurface; фон Activity тёмный. Цвет первого native/GPU буфера после отправки lease неизвестен.
HUD получил такую же проверку успешной отправки текущей lease, как приборка; в обеих метках
первого update добавлен SurfaceTexture timestamp. Ожидание tiles/MapLoaded, bitmap readback и
обязательный producer ACK **не добавлены**: они ранее оставляли карты пустыми (NAV-019).

## Проверки и открытая приёмка

Локально выполнены 46 JUnit-проверок изменённого reducer, кэша с зависшим диском и разбора key
records (Android boundary doubles для инфраструктуры), 154 проверки инструментов после
обновления фикстур и компиляция всех 38 Navigator Java файлов против Android API 28. Итоговые
полная Android сборка, тесты, подписи и байтовая проверка APK записываются в протоколе 2.9.4.

Первый source CI [34810287441](https://github.com/AGKulikov/Status/actions/runs/34810287441)
скомпилировал всё Android-приложение и выполнил 1893 теста; один прежний текстовый контракт
NavigationHudV2ContractTest ещё требовал размер без shadow union. Обновлены его проверки полных
границ и независимой композиции камер, которые уже проверены исполняемыми fixtures. После
этого 32 теста NavigationHudV2ContractTest/PassiveMediaKeyContractTest прошли локально. Первая
неуспешная проверка не скрывается и не считается готовым выпуском.

На KX11 остаются: холодный старт/обновление без Settings и белой вспышки; ANCS без перезагрузки;
длительное переключение несколькими плеерами с реальными нажатиями; три состава камер,
отсутствие нижних дубликатов и ДТП; светофоры с хвостиком на восьми сторонах при движении,
масштабе и обеих темах. Достоверный полный источник штатной «Поездки 2» не получен: отсутствие
полей не заменяется вычисленными оценками или PA-данными, ранее отвергнутыми фотографиями.
