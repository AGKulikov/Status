# Обновление требований и описания Natro

Этот порядок уточняет REL-013, прежний раздел «Как вести этот файл» и DOC-READ-20261124-R2. Источник решений — [полный реестр](../../PROJECT_REQUIREMENTS_RU.md), актуальная навигация — [карта уточнений](../CURRENT_REQUIREMENTS_RU.md). Выборки формируются из исходных строк: генератор **не определяет сам**, какое историческое правило заменено и какой статус действует сегодня.

## Когда и что записывать

Записывать новый факт: требование, поправку, отказ, отмену, результат проверки, существенный вывод исследования. Обычный вопрос «готово?» или повтор прежнего поручения без изменения условий не требует нового ID и копии всей истории. При появлении новых данных обновляется соответствующая запись состояния/отчёт. Это уточняет старое правило «после каждого нового сообщения» и предотвращает повторное разрастание реестра.

| Событие | Запись в полном реестре | Карта уточнений и описание |
|---|---|---|
| Новое самостоятельное функциональное требование | До реализации добавить в конец одну каноническую строку с новым ID, формулировкой и проверяемым критерием; рядом дату, источник решения, область и связи | В карте — краткий актуальный статус со ссылкой, если меняется задача/поведение; README не объявляет функцию готовой |
| Поправка или отмена существующего требования | Сохранить ID требования; добавить датированное уточнение с точным заменяемым фрагментом, новой формулировкой и основанием. Каноническую строку с тем же ID повторно не создавать | Обязательно заменить соответствующее действующее уточнение, указать источник и область замены. Не отменять незатронутые части |
| Независимое требование, заменяющее другое | Новый ID; в дополнении явно связать «заменяет старый ID/часть». Старые строки не удалять | В карте указать действующий ID и связь замены |
| Результат сборки, проверки или отказ пользователя | Использовать прежние ID; добавить результат, версию/коммит, дату, источник и уровень доказательства. Новый ID только ради изменения статуса не нужен | Обновить затронутый статус/открытый дефект; успешный тест не закрывает FIELD |
| Исправление ошибки в документации | Добавить короткую поправку, если меняется смысл/доказательство; архивную формулировку сохранить. Опечатки в рабочем описании исправлять прямо | Обновить затронутый документ; новый APK и новый номер приложения не требуются |

Новый канонический ID имеет формат `FAMILY-NNN` (латинские заглавные буквы, дефис, три цифры). Проверить, что он не занят **во всём реестре**, включая прозу, через поиск ID и семейства. Уже существующие длинные/повествовательные ID сохранять; массово не перенумеровывать. Перенос такого требования в таблицу — явная структурная операция с тем же смыслом, а не присвоение его ID другой функции. При новом семействе добавить ссылку и зависимости в [маршрут чтения](README_RU.md).

Каноническая таблица: `| ID | Требование | Статус / критерий |`, одна строка на ID и три содержательные ячейки. Новые строки размещать под датированным заголовком в конце файла. Старую архивную часть и прежние доказательства не переписывать. Уточнение существующего ID писать текстом вне новой канонической строки; указать дату и устойчивый заголовок/ссылку. S-ссылка с хешем пригодна для чтения конкретной редакции, но не заменяет постоянную ссылку на решение.

Минимум содержательной записи: что требуется; где и при каких условиях; что заменяет (или «новое, ничего не заменяет»); основание пользователя/доказательство; связанные ID; как проверить; какие SOURCE/TEST/APK/PUBLISH/FIELD подтверждены или открыты. Решение пользователя не заменять догадкой о реализованном поведении. При неизвестном критерии записать пробел и уточнить только зависимую часть задачи.

## Какие документы менять вместе

- `PROJECT_REQUIREMENTS_RU.md` — новые решения и доказательства; история добавляется в конец.
- `docs/CURRENT_REQUIREMENTS_RU.md` — короткая действующая формулировка, статус, ссылка на замену/доказательство. Не копировать сюда протоколы целиком; отсутствие пункта в карте не отменяет исходное требование.
- `README.md` — назначение проекта, фактические возможности/ограничения, актуальная рабочая ветка и **последний подтверждённо опубликованный выпуск**. Менять при изменении этих фактов, не только после APK. Реализованное лишь в исходниках обозначать с коммитом и отсутствием APK; план/новое требование не выдавать за доступную функцию. Счётчики тестов подписывать областью и версией: проверка документов не меняет старые результаты сборки 3.5.7.
- `docs/releases/<version>/README_RU.md` и отчёты — состав и доказательства конкретного выпуска. Новый кандидат не подменяет в README текущий опубликованный релиз. После публикации проверить доступность артефактов и согласованность версии/ссылок в README и карте состояния.
- Профильная инструкция, база Geely, исследовательский отчёт, открытый вопрос, индекс исследований — только если меняются соответствующие сведения. Текущий отчёт задачи хранит незавершённую работу и следующий шаг; история выпусков не накапливается в README.
- `COMMON_RU.md`, `modules/*.md`, `index.json` — только через генератор. Исторический CSV и ZIP остаются снимками; их не переписывать при обычном обновлении. Git хранит последующие версии документов.

## Завершение обновления

1. Сверить смысл между решением пользователя, дополнением реестра, картой и описанием: одна действующая формулировка, чёткая область замены, без преждевременного «исправлено». Не расширять приёмку или отмену на другие версии/экраны без основания.
2. Выполнить `python tools/requirements.py build`, затем `python tools/requirements.py check`. Проверить поиск изменённого ID и темы: новая запись находится, нет второго канонического ID, маршруты/ссылки работают. Структурная проверка не заменяет содержательную сверку README и карты.
3. При изменении структуры/генератора выполнить `python -m unittest tools.tests.test_requirements_reader -q`. При обычной текстовой поправке достаточно проверки структуры, ссылок и смысла; повторный полный CI приложения не нужен. Проверки приложения определяются изменениями кода и критериями требования.
4. Просмотреть diff: исходные решения сохранены, архив неизменён, в публичные документы не попали приватные данные. Сохранить источник, выборки, описание и относящиеся доказательства одним согласованным изменением.
5. Опубликовать в актуальную ветку, проверить удалённый commit/tree и ссылки. При несовпадении головы ветки сначала сверить чужие изменения и новые ID; не перезаписывать их. Если публикация не состоялась, обозначить «только локально», не говорить «обновлено в репозитории».
