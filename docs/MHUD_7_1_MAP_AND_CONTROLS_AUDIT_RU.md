Дата: 03.10.2026. Статус: **STATIC / локальный replay; аппаратная проверка OPEN**.

Исполняемый код Natro в этом изменении не менялся; APK не собирался.

## Как проходит карта

`MinimapBroadcaster` создаёт отдельный `OffscreenMapWindow` в процессе Навигатора.
Он берёт маршрут из `LaneSignListener`, использует собственный location manager,
задаёт камеру и рисует миникарту. Далее:

1. `captureScreenshot()` возвращает bitmap; захват вызывается на MAIN Навигатора.
2. Отдельный `MhudMinimapJpeg` сжимает изображение в JPEG quality60.
3. `com.yandex.MINIMAP` передаёт байты `minimap_jpeg` явным broadcast установленным
   получателям `plus.monjaro`, mHUD и его dev-пакету.
4. `YandexMinimapReceiver` оставляет в `AtomicReference` последний ожидающий пакет.
   Один executor декодирует JPEG; `is.g` переиспользует два mutable `inBitmap`.
5. При появлении более свежего пакета декодированный устаревший результат пропускается.
   Публикация через `a8.run` делает отдельную immutable-копию bitmap на MAIN mHUD;
   прежняя опубликованная копия освобождается отложенно. Это не путь без копирований.
6. `MirrorPresentationService.af` / `xg.cl` / `tg.f` показывают bitmap в `ImageView`.
   Размер кадра запрашивается по размеру виджета, с выравниванием по8 и границами96…1920.

| Свойство | Исследованная пара | Natro3.0.1 / текущее дерево |
|---|---|---|
| Передача карты | Screenshot → JPEG → broadcast → decode → bitmap copy → ImageView | OffscreenMapWindow → `SurfaceFactory.from` → `addSurface` → TextureView; без JPEG и постоянных screenshot |
| Частота | `setMaxFps(8)`; цикл и минимальный интервал отправки150мс, то есть максимум около6,7 отправки/с без учёта затрат | Настраиваемый потолок1…60; defaults HUD30, приборка60; приборка ограничивается15 на стоянке |
| Детализация | Принудительная ночь, выключены модели/indoor и ряд декоративных слоёв; выбранный вид может включать3D-дороги | Независимые профили HUD/приборки, день/ночь и дополнительные маршрутные слои |
| Работа без потребителя | ENABLE/DISABLE; stale heartbeat20с выключает миникарту; опциональный idle после окончания маршрута | Собственный lifecycle Surface/bridge и `BackgroundMapLease`; проверять фактический demand, не считать его отсутствующим |
| Управление очередью | Один JPEG в обработке на стороне источника, последний пакет на стороне приёмника | Прямое производство кадров в Surface; пакетной JPEG-очереди нет |

Экономию mHUD объясняют прежде всего низкая частота, размер миникарты и облегчённые
слои. Заявление «максимально оптимизирована» не подтверждено: есть GPU readback,
JPEG encode/decode, broadcast, дополнительная копия bitmap и работа на MAIN.
В `captureOnce` нет вызова имеющегося `shouldSendFrame`; одно наличие этого метода
не означает, что одинаковые по положению/камере кадры действительно отбрасываются.

MapKit официально описывает `OffscreenMapWindow` как карту без собственного View,
способную рисовать на внешние поверхности, и `setMaxFps` как способ уменьшить затраты
CPU/GPU при допустимой меньшей плавности:
[OffscreenMapWindow](https://yandex.com/maps-api/docs/mapkit/com/yandex/mapkit/map/OffscreenMapWindow.html),
[MapWindow](https://yandex.com/maps-api/docs/mapkit/com/yandex/mapkit/map/MapWindow.html).
Эти документы подтверждают API, а не быстродействие исследованных APK.

## Что это говорит о белом свечении

В моде перед первым screenshot проходит не менее800мс от `sStartUptime`, который
фиксируется после настройки карты. Ночной режим включён принудительно. Внешней
MapKit Surface на HUD в этой цепочке нет: пользователь получает готовый bitmap,
поэтому промежуточный буфер создания внешней Surface не передаётся напрямую.
При отсутствии bitmap живой `ImageView` может оставаться пустым/скрытым либо
сохранять прежнее изображение; редактор умеет показывать демонстрацию.

**Проверки на белый кадр в просмотренном пути нет.** `captureOnce` проверяет
наличие bitmap и ширину; приёмник проверяет пакет, успешность decode и recycle.
`tg.f` устанавливает изображение, `tg.c` обрезает форму; они не отбрасывают белые
пиксели. Если screenshot после800мс белый, этот путь тоже способен его показать.
Отсутствие свечения на автомобиле с данной парой пока не подтверждено логом/видео.

У Natro профиль и фон уже настраиваются до `addSurface`; одного повторения этого
шага недостаточно. Найдено конкретное ограничение защиты3.0.1:
`MapBootstrapPolicy.mayReveal` разрешает показ при elapsed>=800 независимо от
`white`; независимый timeout в `MapStartupPresentation` также вызывает `finish`.
Это намеренный выход из зависшего старта, введённый после отказа карт, но он не
гарантирует устранение белой вспышки.

На неизменённом production-классе выполнен Java replay:

| Вход | Результат `mayReveal` |
|---|---|
| Белый кадр, успешная выборка,2 кадра,200мс | false |
| То же,799мс | false |
| То же,800мс | **true** |
| Копирование недоступно,800мс | true |
| Небелый кадр, успешная выборка,2 кадра,200мс | true |

Это доказательство возможности раскрытия белого буфера в логике, не доказательство
его происхождения на GPU и не подтверждение того же пути в последнем эпизоде KX11.

## HUD и «машинки»: сравнение с ADB-скриптом

| Действие | Механизм в исследованном mHUD7.1 |
|---|---|
| HUD | `hud_projection_enabled`; класс `s3`: включено→1, выключено→0; базовый AdaptAPI ID `0x20110100` (537985280); `CB_VF_HUD_ActvReq`, manager ID32922 |
| «Машинки» | `hud_show_ar_cars`; класс `t3`: показывать→0, скрывать→1, то есть явная инверсия в коде; базовый AdaptAPI ID `0x27020200` (654443008); `CB_VF_HUD_ARActvReq`, manager ID32928 |
| Запись через Android | HUD: ключ `CB_VF_HUD_ActvReq`; AR: `CB_VF_HUD_ARActvReq` и `CB_VF_HUD_ARActivityReg_OnOff`; попытки записи в Global/System/Secure напрямую и через PrivilegedShell |
| Запись через автомобильные API | Попытки `ICarFunction.setFunctionValue` без зоны и с зонами `Integer.MIN_VALUE`,1 и полученными supported zones; также `ECarXCarVfhudManager` и property manager. Найденные по имени поля/методы добавляются динамически |

Это несколько попыток управления функцией, а не один доказанно достаточный вызов.
Код делает readback/logging, но сохранённый checkbox и совпавшая запись Settings
не доказывают физического результата. В коде также есть повторы с отменой старого
поколения; их нельзя переносить как готовую безопасную политику Natro.

Прежний `hud_lca_standalone.sh` делает другое: с root/remount заменяет **32 байта
по смещению124248** в `vendor.ecarx.xma.automotive.vehicle@1.0-modules.so`
размером268424. Только для разрешённых SHA он подменяет IntellDrv(1) на
Simple(3), IntellGuide(0) или AR(2); есть побайтовая проверка и восстановление.
Оригинальный SHA256 `b5bcf37a0aa8a31bf69296989ba7730ded54f99998f43a6313af4e4a4180cca6`.
Скрипт ограничен SDK28/arm64 и точным модулем, новый файл используется после
перезагрузки. Ни такого патча, ни его применения в разобранных HUD/AR-переключателях
mHUD нет. Одинаковый ожидаемый внешний эффект не делает механизмы одинаковыми.

Переключатель HUD адресует активность самой проекции; его нельзя выдавать за
безусловное скрытие только штатной графики с сохранением нашей карты. AR-команда
не идентифицирует владельца штатной центральной машинки/крыльев DIM и не равна
патчу режима HUD/LCA. На прежнем снимке KX11 `HUD_ACTIVE` был active, тогда как
`HUD_AR_ENGINE` — notavailable. Наличие менеджерского маршрута в каталоге не
снимает это ограничение и не подтверждает поддержку текущей прошивкой.

## Предложение для накопительной версии

1. Сохранить прямой Surface-путь и независимые карты HUD/приборки. JPEG-перенос
   не даёт доказанной выгоды и меняет плавность/качество. Снижение FPS допустимо
   только отдельным выбранным профилем; существующие настройки не ухудшать молча.
2. При проверке старта разделить источник белого буфера и момент его раскрытия.
   Сопоставить producer configure/addSurface, generation, первый callback,
   результат малой выборки и `bounded_fallback` с видео HUD/приборки.
3. Проверить на точном MapKit30.3.0 подготовку не светящегося начального кадра
   до его вывода. Пересмотреть раскрытие **положительно определённого белого**
   кадра по deadline отдельно от отказа самой выборки. Конкретная схема требует
   ограниченного восстановления и проверки на KX11; не возвращать бесконечное
   ожидание tiles/MapLoaded/ACK/PixelCopy и не скрывать живую карту при resize.
   Простое увеличение800мс не считать исправлением причины.
4. Проверить demand/lifecycle при отключении карты, исчезновении потребителя и
   окончании маршрута. Критерий экономии — парное измерение CPU/GPU/памяти при
   одинаковых размерах, слоях и FPS, затем отдельный замер облегчённого профиля.
5. HUD/AR рассматривать отдельно от карты. Перед возможным переносом установить
   один поддержанный маршрут точной прошивки, исходное значение и readback,
   затем независимо проверить физический эффект и возврат. Массовые записи по
   похожим именам, во все namespaces/zones и автоматические повторы не переносить.

Предложение не меняет NAV-019/020/021 и не закрывает GATE-107, CLUSTER_WINGS или
HUD_PROFILE. Команд на автомобиль, записи системной библиотеки и новой сборки APK
в рамках разбора не было. Полный отказ кнопок3.0.1 остаётся отдельным открытым дефектом.
